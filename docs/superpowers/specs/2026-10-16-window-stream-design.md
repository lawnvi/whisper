# Window Stream Design（窗口流转）

## Goal

让应用窗口在设备之间流转：在一台设备上实时看到另一台设备上的某个应用窗口，并且可以直接操作。鼠标、键盘、触摸和中文输入都会回到原设备的那个窗口。

| 方向 | 说明 | 阶段 |
|---|---|---|
| 安卓 → 电脑 | 手机应用在电脑上各开一个窗口，用电脑的键鼠操作 | 第一阶段 |
| 电脑 → 安卓、iPad、iPhone | 电脑上的窗口拿到手机或平板上看、操作 | 第二阶段 |
| 电脑 → 电脑 | 包括没接显示器的电脑（比如当服务器用的机器） | 第三阶段 |

不做的方向：安卓 → iOS，手机 → 手机。iOS 只做接收端。

地基要按"任何来源、任何接收端"来设计。加一个新方向时，只新增一个来源或接收端的实现，不改中间层。

## Why This Matters

- Whisper 已经能在设备之间传文件、文字、剪贴板、声音和键鼠。窗口流转补上最后一块：应用本身也能在设备之间移动。
- 安卓 → 电脑的需求最明确：各手机厂商的"多屏协同"只支持自家设备，跨品牌、Mac 和 Windows 都能用的方案还是空白。2026-10-16 用户在小米 17 和 MacBook Air 上亲手试过（scrcpy 虚拟屏 + 手机布局 + Wi-Fi + 声音同步），体验可以接受。
- 已有的手机控制器（`docs/superpowers/specs/2026-10-06-mobile-controller-*.md`）能用手机操作电脑，但"无屏幕回传"。电脑 → 手机这个方向补上的就是画面。
- 参考了 [sill](https://github.com/Saffsanity/sill)（Mac 单窗口到 iPad，Apache-2.0）的设计。下文标注 sill 的地方，都是它实测过的做法。

## Confirmed Scope

- **来源分两类**，对上层是同一个接口：
  - **本机抓取来源**：macOS（ScreenCaptureKit + VideoToolbox），以后加 Windows（Windows.Graphics.Capture + Media Foundation）和 Linux X11。画面走 Whisper 自己的加密通道 `/window`。
  - **安卓来源**：由电脑端 Whisper 通过 USB 或安卓自带的无线调试，启动随包附带的 Whisper 手机端程序 whisper-agent（基于 scrcpy-server 5.0.1 改写，Apache-2.0）。一个进程管理所有窗口；画面、声音、控制都走 adb 通道，无线时这条通道本身有 TLS 加密。随包同时带官方 scrcpy-server 5.0.1 作为兜底。
- **接收端三类**：
  - 桌面：每个流转窗口是一个原生窗口；
  - 安卓：MediaCodec；
  - iOS / iPadOS：VideoToolbox。
- 每个流转会话带 `streamId`；同一台接收端可以同时开多个窗口。
- 输入统一成"窗口内比例坐标 + 按键 + 文字提交"三种事件。发往本机抓取来源时走现有 `/input` 手动模式；发往安卓来源时转成 scrcpy 的控制消息。
- 只对已信任配对的设备开放。已信任的设备直接允许，不再每次询问。
- 新增能力位，协议版本升到 12，可以回退到 11、10、9。

## Non-Goals

- 不做安卓 → iOS，也不做手机 → 手机。
- 不做整桌面远程控制，也不做公网中继。
- 不承诺锁屏后还能抓画面或操作。实测结果见"P0 结果"。
- 不做 Linux Wayland 来源：每次都要用户在系统弹窗里授权，体验不合格。
- 不做"笔记本合盖装包"这个场景：实测 Mac 合盖后，靠系统能力和虚拟屏都抓不到画面。

## Approaches Considered

### 安卓来源怎么拿画面和控制

- **A. 普通权限（MediaProjection + 无障碍）**：每次都要在手机上确认，锁屏就停，只能投手机屏幕上正在显示的内容，控制只能做点按。不采用。
- **B. Shizuku**：原版自 13.6.0（2025-05）起没有再更新，Android 16、17 上已经有用户服务启动失败的报告。不采用。
- **C. 自己写 shell 身份的手机端**：要处理一万行量级的系统隐藏接口和机型差异。不采用。
- **D. 原样随包带 scrcpy 手机端**：机型适配交给上游，但缺 UI 树、暂停、最近任务、挪动任务、按应用录音，而且一个进程只管一块虚拟屏。只作兜底。
- **E. 基于 scrcpy-server 改写 Whisper 自己的手机端（whisper-agent）**：上游文件尽量原样保留、记录补丁清单，新能力放在自己的包里，跟进上游新版本时机械合并。**采用**（2026-10-16 用户确认）。

### 数据面放在哪里（本机抓取来源）

**原生只做编解码，压缩后的帧经过 Dart，走现有加密媒体通道。** 认证、令牌、证明握手、XChaCha20-Poly1305 信封都只有一份实现。2026-10-16 在 M4 MacBook Air 上实测：

| 环节 | 32 KB 普通帧 | 1.5 MB 关键帧 |
|---|---|---|
| libsodium 加密加解密 | 0.09 ms | 4 ms |
| WebSocket 本机回环，服务端→客户端（不加掩码） | 0.2 ms | 1.2 ms |
| WebSocket 本机回环，客户端→服务端（Dart 加掩码） | 0.4 ms | 13 ms |
| 开着 dart:io 默认压缩 | 2–3 ms | 65–85 ms |

三条硬性约束：

1. 视频收发放在独立 isolate；
2. 视频沿"服务端→客户端"方向流动；
3. 显式关闭 WebSocket 压缩。

### 输入走哪条通道（本机抓取来源）

复用 `/input` 手动模式，新增按窗口定位的事件。有序注入、心跳、失联释放、文字回执和跨平台键位表，手机控制器都已经在 Mac、Windows、Linux 上做完并实测过。一个流转会话持有一个视频流和一个输入会话；其中任何一个断开，都整体结束并释放按键。

## Architecture

```
            ┌──────────── 来源（WindowSource） ────────────┐
            │                                              │
   本机抓取来源（Mac / Windows / Linux X11）        安卓来源（电脑端适配器）
   SCK / WGC / XComposite → 硬件 H.264            adb ─ scrcpy-server（虚拟屏 + 应用）
            │  /window（Whisper 加密）                     │  adb（TLS）
            ▼                                              ▼
   ┌──────────────── 流转中间层（lib/window_stream/） ────────────────┐
   │ 会话状态机 · 目录 · 发送队列（只保留最新帧） · 统计 · 输入路由       │
   └───────────────────────────────────────────────────────────────┘
            │                       │                        │
      桌面接收端                安卓接收端                  iOS 接收端
   原生窗口 + 解码器          MediaCodec + View      VideoToolbox + 原生视图
   键鼠 / 输入法采集          触摸 / 触控板 / 键盘      触摸 / 触控板 / Pencil / 键盘
```

### 核心接口（`lib/window_stream/core/`，平台无关）

```dart
abstract interface class WindowSource {   // whisper-agent / 兜底 scrcpy；以后 Mac、Windows、Linux
  SourceInfo get info;                    // 稳定设备 id、平台、能力位
  ValueListenable<SourceState> get state;
  Future<List<AppEntry>> apps();
  Stream<List<TaskEntry>> tasks();         // 运行中 / 最近任务；桌面来源对应窗口
  Future<Uint8List?> icon(AppId id);
  Future<Uint8List?> snapshot(TaskId id);
  Future<StreamHandle> open(OpenTarget target, StreamOptions options);
}

abstract interface class StreamHandle {
  StreamId get id;
  ValueListenable<StreamState> get state; // opening / live / suspended / reconnecting /
                                          // displaced / secureBlocked / appExited / closed
  VideoChannelSpec get video;             // sealed：adb socket；以后 Whisper /window 路由
  AudioChannelSpec? get audio;
  Future<void> setViewport(Viewport v);
  Future<void> suspend();
  Future<void> resume();
  Future<void> close({CloseMode mode = CloseMode.returnToSource});
  void sendInput(WindowInputEvent e);     // pointer(0–1) / scroll / drag / key / text
  void requestKeyframe();
  void setQuality(QualityTier tier);
}

abstract interface class WindowSurface {  // 每个流转窗口一个；Mac 由原生插件实现
  Stream<SurfaceEvent> get events;        // 输入、关闭、尺寸、遮挡、聚焦、拾取
  Future<void> setVisual(SurfaceVisual v);
  Future<void> setHighlights(List<Rect01> rects);
  Future<void> dispose();
}
```

- 能力位区分来源的差异，例如 `detachesFromSourceScreen`：安卓是"把任务搬走"，Mac 当来源时是"镜像窗口"，公共层不假设任何一种。
- 画面和声音不经过这些 Dart 接口：数据 isolate 按 `VideoChannelSpec` 读数据、解帧，再用 FFI 直接写进原生显示面的内存。
- 界面、自动化规则和以后的 AI 都通过 `DeviceControl`（看：UI 树、截图；做：点、滑、输入、打开）操作，带审计日志和限速。

## 安卓来源（第一阶段的重点）

### 连接和启动

- 手机端只需要：打开开发者选项里的"无线调试"（或插 USB）；小米还要打开"USB 调试（安全设置）"。
- 电脑端 Whisper 直接讲 adb 服务协议（5037 端口），不调用 adb 命令行：用 `host:track-devices` 监听设备，转发、shell、推送、配对都走协议。只有服务没在运行时才启动它；和 Android Studio 共用同一个服务（两个服务抢不到同一台 USB 设备）。
- 无线调试首次用二维码或配对码配对，之后用局域网发现（`_adb-tls-connect._tcp`）找到端口自动连接。
- whisper-agent（`android_agent/`，`script/build_window_agent.sh` 用 javac + d8 构建，产物可复现）：
  - 上游 scrcpy-server 5.0.1 的源码原样放在 `upstream/`，一行不改；我们的代码在 `com.vireen.whisper.agent` 包里，只调用上游的系统接口封装、`NewDisplayCapture`、`Controller`、`Streamer`；
  - jar 推到 `/data/local/tmp/whisper-agent-<jar 哈希前 16 位>.jar`，推之前用 `sha256sum` 核对，旧版本 jar 顺手删掉；用 `app_process` 以 shell 身份启动；
  - 启动令牌放在环境变量里（exec 之后只有 shell 和 root 读得到），不放命令行；
  - 所有连接共用一个抽象 socket，经一个 `adb forward` 到电脑。每条连接先发 hello：`WAG1`、角色、窗口号、32 字节令牌；agent 先查对端 uid（只认 0 和 2000），2 秒内收不到正确的 hello 就断开；
  - 一条控制连接：长度前缀的 JSON 请求和事件（`hello`、`apps`、`icon`、`tasks`、`snapshot`、`open`、`close`、`suspend`、`resume`、`keyframe`、`bitRate`、`uiTree`、`shutdown`）；
  - 每个窗口三条连接：视频、声音、输入，沿用 scrcpy 的媒体格式和控制消息，电脑端的解析和输入映射原样复用；
  - 最后一条控制连接断开 20 秒后，agent 释放所有虚拟屏并退出，电脑端崩溃也不会把应用留在看不见的屏幕上。
- 应用目录、图标、最近任务和快照都由 agent 提供，不经过手机 Whisper 应用。手机 Whisper 应用只额外提供一个 content provider，让电脑端读到它的对端 id，用来和 Whisper 里的设备对应起来。

### 打开、关闭、暂停

- 打开：新建虚拟屏（不带"移除时销毁内容"标记），已在运行的任务用 `moveRootTaskToDisplay` 原样挪过去，没在运行的再启动。
- 关闭：释放虚拟屏，任务回到手机后台。Android 17 上任务自己留在后台；Android 13 会把它顶到手机最前面，所以 agent 释放前记下手机前台（`getTasks` 的第一个任务，桌面也算），释放后若被顶上来，就用 `startActivityFromRecents` 恢复原来的前台，原来是桌面就回桌面。
- 暂停：编码器 `PARAMETER_KEY_SUSPEND`，虚拟屏和应用照常运行；恢复时请求关键帧。另有"休眠"模式（拔掉编码器输入，虚拟屏关闭、应用挂起）。
- 任务事件：用 `ITaskStackListener` 上报"被拉回手机""应用退出""回到前台"，电脑窗口显示对应状态。

### 画面、声音、控制

- 视频用 H.264，帧头带 PTS 和关键帧标记，电脑端自己解码（VideoToolbox），方便截帧和文字识别。
- 声音按应用（UID）录，只录流转出去的应用，手机上其他应用照常出声。USB 用原始 PCM，Wi-Fi 用 Opus。电脑端用同一个同步器播放画面和声音。
- 控制：
  - 点击、滑动、滚动转成触摸注入；短剧这类上下翻页默认把触控板滚动转成拖动；
  - 文字输入分三档：ASCII 用按键；可编辑的输入框用无障碍的 `ACTION_SET_TEXT` 在光标处插入；其他情况用剪贴板粘贴，用完还原手机剪贴板；
  - 虚拟屏的输入法策略设成隐藏，手机上不弹软键盘。
- UI 树：agent 以 shell 身份连接 UiAutomation，只在检查器打开或规则运行时连接，空闲 30 s 断开。

### 已知限制

- **手机锁屏后，虚拟屏上的应用会停止绘制**（2026-10-16 实测：每 3–4 秒只画约 1 秒）。流转期间手机熄屏但保持唤醒，用户已接受。
- **小米手机要打开"USB 调试（安全设置）"**，否则模拟输入会报 `INJECT_EVENTS` 权限错误。
- **手机重启后要重新打开无线调试。**
- **开了防截屏的应用投出来是黑的**，窗口里明确提示"此应用禁止投屏"。
- UiAutomation 连上时，所有应用都会认为系统开着无障碍服务；部分银行、反诈应用会提示风险，所以只在需要时连接，并支持应用拒绝名单。

## 本机抓取来源（第二、三阶段）

- **Mac 抓取**：
  - `SCContentFilter(desktopIndependentWindow:)`，NV12，`showsCursor = false`，只编 `complete` 状态的帧；
  - 没有接收端时完全不抓。
- **Mac 被挡住的窗口**：
  - 流转期间，把窗口挪到 Whisper 建的虚拟屏上（私有接口 `CGVirtualDisplay`），结束后放回原处（sill 的做法）。
  - 2026-10-16 实测（开盖）：窗口在虚拟屏上时，用户在主屏正常使用，它仍稳定在约 29 帧。
  - 虚拟屏创建失败时，退回"窗口留在原地流转、交互时置前"。
- **编码**：
  - H.264，实时模式，不用 B 帧，关键帧间隔约 4 s，按需插入；
  - 编码器里同时只放一帧，后面只留一个空位，新帧顶掉还在等的旧帧（sill 的 EncoderMailbox）；
  - 一帧卡住超过 1.5 s，就换软件编码、分辨率减半，之后每 30 s 再试一次硬件。
- **尺寸**：接收端窗口的尺寸和密度发过来后，来源用辅助功能把窗口改成对应大小；结束时还原（sill 的 WindowRestore 规则）。
- **输入**：
  - 原生代码按 `windowId` 实时查询窗口位置（缓存 100 ms），把比例换算成屏幕坐标；
  - 点击或按键时，如果目标应用不在前台，先激活并置前，期间的输入暂存，最多等 0.6 s 后按顺序补发（sill 的做法）。
- **没接显示器的电脑**：
  - Mac mini 这类机器用同一块虚拟屏，但"没接显示器"和"合盖"不是同一种状态，要在真机上测过才算支持。
  - Linux 用 X11 虚拟屏（Xvfb 或 dummy 驱动），这是标准做法。
  - Windows 没有显示器时需要虚拟显示驱动，和"不做驱动签名"的约定冲突，暂不支持。
- **Windows**：
  - Windows.Graphics.Capture 能抓被挡住的窗口；最小化的窗口抓不到，计划"移到屏幕外"，要实测；
  - 以管理员身份运行的窗口，要借现有的锁屏服务才能注入输入。

## 协议（本机抓取来源）

### 控制面（聊天通道）

- `MessageEnum` 末尾追加 `WindowStreamControl`（Drift intEnum，只能追加）。
- 动作：
  - `request`：接收端发起，带接收能力和窗口尺寸；
  - `accept`：带一次性 `transportToken` 和编码参数；
  - `reject`；
  - `stop`：带原因码；
  - `sourceState`：锁屏、睡眠、权限被撤销、窗口已关闭。
- **谁同意、谁提供媒体路由；谁发起、谁拨号。** 接收端拨号到来源的 `/window`，视频沿"服务端→客户端"方向流动，不需要加掩码。
- 能力位：
  - `windowStreamSourceV1`：本机抓取来源；
  - `windowStreamSinkV1`：接收端；
  - `windowStreamAndroidAdbV1`：手机上的 Whisper 能提供应用目录、配合无线调试；
  - `remoteInputWindowTargetV1`：能按窗口定位注入。

  这几个位只在协议 12 的 wire profile 里出现，要同步更新 `PeerCapabilities.toWireJson` 和 `fromWireJson` 的允许名单（`lib/state/peer_profile.dart`）。`PeerSocketSession.protocolVersion` 升到 12。

### 媒体面（`/window`）

- 新路由 `/window`，命名空间 `window-stream`，要加进三处：
  - `session_upgrade_token_registry.dart` 的允许名单；
  - `svrmanager.dart` 的路径检查；
  - `packet_byte_transport.dart` 的队列策略选择。
- 认证沿用 `/audio`、`/input` 的令牌 + 证明握手，以及媒体密钥派生的逐包 AEAD 信封。
- 显式关闭 WebSocket 压缩。`IOWebSocketChannel.connect`（web_socket_channel 3.0.3）没有压缩参数，要改用 `WebSocket.connect(..., compression: CompressionOptions.compressionOff, customClient: ...)`，再用 `IOWebSocketChannel(webSocket)` 包一层。
- 包格式：
  - 魔数 `WWS1`；
  - 视频帧用定长二进制头：`type u8 | streamId u16 | frameSeq u32 | captureMicros u64 | flags u8`；
  - 其余消息沿用 `framed_packet_codec` 的 JSON 头。
- H.264 按长度前缀（AVCC）传，参数集单独用 `codecConfig` 消息发。
- 消息类型：

| 方向 | 消息 |
|---|---|
| 来源 → 接收端 | `codecConfig`、`videoFrame`、`catalog`、`thumbnail`、`appIcon`、`cursorShape`、`streamState`、`pong`、`linkReport` |
| 接收端 → 来源 | `open`、`close`、`viewport`、`keyframeRequest`、`ping`、`viewerStats`、`windowCommand`、`launchApp`、`catalogSubscribe` |

- 不认识的消息类型直接跳过。每个方向各自限制负载大小：视频帧 8 MiB，其余 1 MiB。

### 输入（`/input` 手动模式扩展）

- `RemoteInputEventType` 新增两种：
  - `windowPointer`：`{streamId, windowId, x, y, action, button}`；
  - `windowScroll`：`{streamId, windowId, x, y, dx, dy, phase}`。
- 键盘、修饰键、`textCommit` 原样复用。

## 数据面

- **stream isolate**：
  - 每端一个后台 isolate，负责连接、证明握手、加解密、发送队列和统计；主 isolate 只处理控制和界面。
  - 主 isolate 把派生好的逐包密钥和令牌交给它。
  - 现有连接代码能不能在后台 isolate 跑，**要在 P0 验证**。
- **FrameBridge**：帧在原生和 stream isolate 之间直接传，不经过主线程。
  - **原生 → Dart**（Mac 抓取）：FFI。Swift `@_cdecl` 导出注册函数，Dart 用 `NativeCallable.listener` 接收回调。P0 要确认发布版裁剪符号后还能查到这个函数，查不到就放进单独的动态库。
  - **Dart → 原生**（各平台解码器）：Mac 和 Windows 用 FFI 直接调用；安卓和 iOS 用 `BackgroundIsolateBinaryMessenger` 发消息，原生一侧用后台任务队列处理（本机 Flutter 3.41.7 的引擎都支持）。
  - 安卓来源的画面在电脑端由 Dart 读出 scrcpy 的视频帧，也走同一个 FrameBridge 送进解码器。
- **发送队列**（`BoundedOutboundQueue.video`）：

| 类别 | 规则 |
|---|---|
| 控制 | 不丢 |
| 视频 | 只保留最新帧；丢过差分帧后进入"等关键帧"状态，等到关键帧前不再发差分帧；积压排空后再请求关键帧 |
| 批量（缩略图、图标） | 同一项新的替换旧的；有视频积压时让路 |

  **丢弃只能发生在加密之前**：解码器要求信封序号连续（`packet_byte_transport.dart:483`）。
- **链路评分**：来源每秒给每条链路打一次分（正常 / 跟不上 / 卡死），跟不上时提示降画质（sill 的 LinkJudge）。

## 接收端

- **桌面**：
  - 每个流转窗口是一个原生窗口：Mac 用 `NSWindow` + `AVSampleBufferDisplayLayer`，Windows 以后用 D3D。不用 Flutter 的多窗口（还在实验阶段）。
  - 窗口标题写"‹应用› · 来自 ‹设备›"。
  - 改窗口大小时，来源跟着改：安卓来源改虚拟屏尺寸，电脑来源改原窗口尺寸。
  - 输入在这个原生窗口里采集，包括输入法提交的文字。
- **安卓**：
  - MediaCodec 低延迟模式，输出到 Surface；
  - 显示方式在平台视图包 `SurfaceView` 和 `Texture` + `SurfaceProducer` 之间，实测后二选一；
  - 手势复用手机控制器的触控板代码，另加"直接触摸"模式。
- **iOS / iPadOS**：
  - VideoToolbox 解码，原生视图显示，Flutter 叠加控件；
  - 支持触摸、触控板、Pencil 和外接键盘（参考 sill 在 Esc、外接键盘上的处理）；
  - 只在前台工作。
- **目录和切换界面**（各接收端共用设计）：按 Apple 的设计理念来做：内容优先，界面退到后面，动效交代空间关系。先做可交互的网页原型并确认，再动手写界面，同时更新 `DESIGN.md`。

## 流转空间：设计语言（2026-10-16 用户要求）

用户原话："流转这里可以想象成一个统一的操作系统，不管是手机、pad 还是桌面端都是统一的设计语言和操作逻辑……最差也要是苹果级别的设计"。

### 一个模型

- **四种对象**：设备、应用、最近任务、窗口。每台设备上的"流转空间"都展示同样的四种对象，只是排版随屏幕变化。
- **窗口有两个属性："运行于"和"显示于"。** 用户说的两种用法都是它的特例：
  - **屏幕延伸**：运行于 A、显示于 B，A 自己的屏幕上不再占位。例如手机应用显示在 Mac 上、手机熄屏；Mac 窗口显示在平板上。
  - **远程操作**：在 A 上直接用 B 的功能，例如在 Mac 上用手机应用，不用碰手机。
- 每个窗口都可以"送到另一台设备上显示"，来源不变。

### 布局

- **桌面**（Mac、Windows、Linux 的 Whisper 主窗口里）：
  - 顶部**设备架**：每台在线设备一张卡片，包括设备轮廓、名字、状态点、正在流转的窗口数；
  - 中部**最近**：选中设备的最近任务，叠成一摞的卡片，悬停时展开；
  - 下部**应用**：图标网格，搜索框在最上方，输入即筛选，运行中的应用下面有小圆点；
  - 右侧**窗口栏**：所有活跃窗口的实时缩略图。悬停时显示控制：暂停 / 继续、静音、聚焦、送到…、关闭；
  - 每个流转窗口本身是原生窗口，不在空间里绘制视频。
- **手机**（竖屏）：同一组对象纵向排列：设备架（横滑）→ 最近（大卡片轮播）→ 应用。
  - 打开窗口后全屏显示，底部悬浮一个控制胶囊：回到空间 / 暂停 / 键盘 / 送到…；
  - 从底部上滑回到空间。
- **平板**：桌面布局的触控版，窗口栏放在左侧，类似台前调度。

### 视觉

- **材质**：
  - 空间背景是很淡的渐变，加上当前设备色调的光晕；
  - 浮层（菜单、控制胶囊、暂停遮罩）用毛玻璃；
  - 卡片用连续曲率圆角（22–28）和多层柔和阴影；
  - DESIGN.md 原先"避免玻璃"的规定只适用于应用外壳的普通页面，流转空间按本节执行。
- **颜色**：
  - 每台设备有一个色调，由设备 id 映射到一组精选色，用在设备卡片、窗口缩略图描边和标题前的小点上；
  - 状态色：直播绿、暂停琥珀、重连蓝（脉冲）、出错红。
- **字体**：系统字体。空间标题 28/700，分区标题 13/600，正文 13–15。

### 动效

- 全部用弹簧：位移刚度约 380、阻尼约 30；缩放更硬一些。
- **共享元素**：点卡片或图标，从它所在的位置放大成窗口；关闭时缩回窗口栏。
- 堆叠悬停时，每张卡片相隔 40 ms 依次展开。
- 窗口状态切换用淡入淡出加模糊过渡。
- 开启"减少动态效果"时全部退化成淡入淡出。

### 交互

- 点应用：在当前设备上打开；按住 ⌥ 点击（手机上长按）：选择"在哪台设备上显示"。
- 把最近卡片或窗口缩略图拖到设备架上的某台设备：送到那里显示。
- 窗口控制在所有设备上一致：
  - 暂停只停画面；
  - 静音单独控制；
  - 关闭会把应用送回来源设备的后台。
- ⌘K：空间搜索，搜所有设备上的应用和窗口。

### 两种操作：拉过来、送出去（2026-10-17 用户要求并确认）

用户原话："把自己的窗口流转到其他设备是当前设备发起的，把其他设备的应用窗口显示到自己屏幕上也是自己发起的，要区分好两种操作的不同，动画什么的都要设计好。"

- **拉过来**（在本机打开别的设备的应用）：入口在那台设备的页面 → 流转 → 点应用或最近卡片。窗口从被点的卡片位置放大，变成本机窗口，先显示快照，第一帧到了再切成实时画面。已实现，动画待按本节打磨。
- **送出去**（把本机的窗口送到别的设备上显示）：入口在目标设备的页面 → 流转 → 新分区"送到 ‹设备›"，列出本机窗口的缩略图。点一个之后：
  - 本机这张卡片缩小，沿弧线飞向设备架上目标设备的卡片，那张卡片用它的色调闪一下；
  - 对方屏幕顶部落下一条横幅（手机上是灵动岛样式），带窗口缩略图和"‹设备› 送来了 ‹窗口›"。点一下，从横幅缩略图放大成全屏查看页；不点就几秒后收起，窗口留在对方的窗口栏里；
  - 对方正在前台用 Whisper 时直接打开，不用再点（用户确认：横幅提示、点开查看）。
- 两种操作在界面上分开：分区标题不同（"‹设备› 上的应用" 对 "送到 ‹设备›"），图标方向不同（向内对向外），动画方向相反（从卡片放大进本机 / 从本机缩小飞出去）。
- 协议：送出去 = 来源发一条 `offer`（窗口 id、标题、应用、缩略图），接收端同意后照常发 `open`、拨 `/window`，复用拉过来的整条媒体链路。`offer` 是唯一由来源发起的会话，方向校验要单独处理。

### 被流转设备上的提示（2026-10-17 已实现安卓）

- 手机上的 Whisper 显示常驻通知"正在流转到 ‹电脑›，N 个窗口正在那台设备上显示，可被操作"，带"停止流转"。Android 16 起申请推广（状态栏胶囊；小米超级岛、ColorOS 流体云这类系统能接住）。
- agent 通过手机 Whisper 的内容提供者（`com.vireen.whisper.window_stream`，只认 shell 和 root）上报窗口数、每秒查询一次停止请求；按下停止后 agent 关掉所有窗口。
- Mac 当来源时，菜单栏的录屏标识就是系统级提示；缩略图串行截取并缓存，浏览时不再反复闪。

### Mac 窗口到手机：照 sill 的做法（2026-10-17 用户确认）

用户试过镜像后说"mac 屏幕上还有流转的窗口……这样的功能感觉没什么用"。问到要不要改成整块扩展屏时，用户答"参考 sill 的方式"。sill 的源码（Apache-2.0）已经读过，照它做：

- **窗口挪走，不是复制。** 手机打开一个 Mac 窗口时，Mac 给它建一块私有的虚拟显示器（`CGVirtualDisplay`，`VirtualDisplay.swift` 改自 sill），用辅助功能把窗口挪上去。手机上看到的就是这个窗口，Mac 屏幕上不再有它。窗口在自己那块屏上不会被挡住，所以一直有画面。
  - 抓取的是那块屏上整个应用（菜单、弹窗、表单都在），再裁成窗口的矩形。
- **回家。** 以下几种情况，窗口都按原来的位置和大小放回去：
  - 流转结束；
  - 手机离开查看页（暂停）；
  - 显示器被系统收走；
  - Whisper 退出（`atexit` 兜底）。
  - 回来时如果 Mac 的指针还在虚拟屏上，也移回原处。
- **大小。** 手机把可用屏幕（逻辑点）和"文字大小"（Aa：0.5 / 0.75 / 1 / 1.25 / 1.5）发给 Mac，窗口大小 = 屏幕 ÷ Aa。
  - 手机默认 0.75，平板默认 1。
  - 虚拟屏按 sill 的"包络"建成边长为（长边 ÷ 0.5）的正方形，转屏或换 Aa 只挪窗口、不重建屏。
  - 应用坚持更大的最小尺寸时，屏只长大一次。
  - 新消息 `viewport` 传这些值，打开时随 `open` 一起带上。
- **退回原样。** 以下情况照旧抓真实窗口：
  - 没有辅助功能或屏幕录制权限；
  - 窗口在别的桌面或全屏空间；
  - 应用拒绝挪动；
  - 虚拟屏建不出来。
- **鼠标。** 虚拟屏对 macOS 是一块真屏，Mac 的指针可以移进去。所以抓虚拟屏时把指针画进画面。
- **延迟。**
  - 编码器里同时只有一帧，新帧替换等待中的旧帧（原来是丢新帧）。
  - Mac 30 ms 没发视频就发一个心跳包（`typeTick`），手机 Wi-Fi 不进省电。
  - 安卓查看时持有 `WIFI_MODE_FULL_LOW_LATENCY` 锁。
- **窗口列表。** 只列屏幕上真实打开的窗口：`onScreenWindowsOnly: true`、第 0 层、大于 100×100。应用隐藏的辅助窗口不再出现（原来一个微信显示成六个）。别的桌面上的窗口也不列，和 sill 一样。

未验证：本次改动时 Mac 和手机都锁着屏，虚拟屏这条路还没真机跑过。

2026-10-17 第二批调整（用户试用后的反馈）：

- **Mac 的鼠标不进虚拟屏**：用户的鼠标跑进看不见的虚拟屏后找不回来。现在有一个"指针围栏"：Mac 自己的鼠标一移进 Whisper 的虚拟屏，就放回刚才的位置。手机点击打上标记，不受围栏限制。虚拟屏画面里不再画指针。
- **安卓上每个 Mac 窗口是单独的任务**：用 `WindowStreamActivity`，一个窗口一个文档任务（`documentLaunchMode=intoExisting`，用窗口编号区分）。
  - 默认横屏，可以旋转；最近任务里显示"窗口名 · 设备名"。
  - 解码器用 `setOutputSurface` 直接画进 activity 的 SurfaceView，Whisper 主界面退到后台也不停。
  - 手势：点按为单击；单指滑动为滚动，并在本地生成惯性；按住为右键；按住后拖动为拖拽；双指轻点为右键。
  - 输入法：自定义 InputConnection，只发送输入法提交的文字，所以拼音可用；横屏时键盘不全屏。
  - 切到别的任务算暂停，一分钟后 Mac 才把窗口放回原处，来回切换不会让窗口跳来跳去。
  - 窗口重新显示或解码器换了画面时，Mac 会把最后一帧再编码一次（静止的窗口不会产生新帧）。
- **安卓窗口在 Mac 上**：可以手动全屏；"缩放"按画面比例铺满屏幕。键盘输入先经过 macOS 输入法，拼音能用；普通按键仍按键码发送。
- **入口**：流转和文件从设备会话页移到了设备列表的工具栏。
  - 桌面：工具栏平时只显示"展开"、二维码、设置，以及正在运行的功能；点"展开"后搜索框缩到左边，露出流转、文件、共享声音、键鼠。
  - 手机：顶栏多一个"更多"按钮，弹出菜单。


### 2026-10-17 第三批（用户第三次试用后）

- **鼠标：改成扩展屏**。用户先说"鼠标进去了回不来"，挡住后又说"移动不过去"，所以现在按扩展屏处理：
  - 虚拟屏的大小就是手机屏幕 ÷ Aa，手机显示整块屏（包括它的菜单栏和指针）；
  - 虚拟屏放在 Mac 所有屏幕的最右侧，鼠标从右边出去就到手机上，往左回来；
  - 窗口在虚拟屏上铺满；手机的触摸换算到整块屏；
  - 键鼠共享的屏幕布局不包含这些虚拟屏；
  - 去掉了指针围栏。
- **延迟（还没实测）**：
  - Mac 的服务器和手机拨号的 `/window` 连接都设置了 TCP_NODELAY，原来小包（输入、控制）可能被 Nagle 算法压住；
  - 发送队列里已有两帧时，编码器先不编码，等发出去后再编最新一帧，原来最多能排 48 帧；
  - VT 编码器设置 MaxFrameDelayCount=0；
  - 手机每秒测一次往返延迟，和收到的帧率、码率一起写进日志。
- **最近任务和窗口合成一件事**：
  - 每台设备只有一个列表（手机是最近任务，电脑是打开的窗口），在本机打开的标"流转中"，点它会把那个窗口调到前面；
  - × 是真的在原设备上关掉：Mac 按窗口自己的关闭按钮，安卓相当于在最近任务里划掉；
  - 右侧的窗口栏和手机上的窗口浮条去掉了；
  - 安卓上独立窗口任务里的 × 改叫"结束流转"，流转结束时也会从手机最近任务里移除。
- **声音**：Mac 播放器原来遇到网络卡顿就加 30 ms 缓冲，而且不再减少；手机和 Mac 的声卡时钟又有细微差异，会慢慢把缓冲耗尽，然后卡一下重来。现在用 ±3% 以内的变速把缓冲稳在目标值，网络平稳 20 秒后再把多加的缓冲慢慢还回去。
- **日志**：流转事件、每 30 秒的统计和音频重启都写进应用数据目录的 `window_stream.log`。

### 2026-10-17 第四批（用户第四次试用后）

- **声音每一两秒卡一下**：上一批用变速把缓冲稳在目标值，实测变速本身每一两秒就造成一次停顿。现在不改速率，缓冲偏多或偏少时，每个包裁掉或补上一帧（和前后帧混合，听不出来）。
- **窗口数量**：只列人能看到的窗口——任一桌面上显示着的（窗口服务器的 ordered-in）、全屏的、最小化的、隐藏应用的。关到菜单栏但还留着的窗口（QQ、飞书之类）不算。实测这台 Mac 从 18 个变成 8 个，和桌面一致。
- **全屏窗口**：全屏的窗口在别的空间里，辅助功能的窗口列表里没有它，原来只能原地流转（看得到、点不了）。现在先找应用的主窗口，不是的话从应用的"窗口"菜单里点它变成主窗口，然后退出全屏、挪到虚拟屏；结束时回原位并重新全屏。试过按元素编号造辅助功能对象、按窗口切换空间，在这台系统上都不起作用，已去掉。
- **结束后窗口留在虚拟屏上**：原生层的停止任务以弱引用排队，会话一释放就跳过了"窗口回原位、移除虚拟屏"。改成强引用。macOS 会记住窗口所在的显示器，虚拟屏每次以同一身份出现时，之前没回去的窗口（实测是微信）会被系统自动搬过来；现在流转期间每秒检查一次，别的应用的窗口出现在虚拟屏上就送回主屏，被流转应用自己的新窗口（对话框等）留下。
- **鼠标**：手机触摸会把 Mac 的指针带到虚拟屏上。现在手指抬起 0.15 秒后指针回到原来的位置；手指操作时手机画面里不画指针，停手 2.5 秒后恢复，Mac 鼠标真的移过去时照常显示。
- **应用图标**：安卓应用流转到 Mac 的窗口，标题栏用该应用的图标（系统默认悬停时显示），最小化后程序坞里显示该应用的图标。每个窗口单独的程序坞图标做不到（要每个应用一个独立进程）。
- **送达提示（灵动岛）**：黑色胶囊在状态栏下方弹出，弹簧变形成卡片（应用图标、来自哪台设备、窗口名，"忽略"和"查看"），内容从模糊中浮现；8 秒后缩回小胶囊，再等 12 秒自己离开。上滑关掉，点小胶囊重新展开。
- **手机首页的功能入口**：去掉彩色方块面板，改成和桌面一样的箭头开关：点箭头，流转、文件两个灰色图标依次从旁边滑出，标题让位；打开功能后自动收起。
- **流转页的应用栏**："显示系统应用"做成紧跟标题的开关胶囊；搜索框加长（桌面 300 pt，手机单独一行）、改成胶囊形；搜索结果变化时留下的应用滑到新位置，新出现的依次长出来，去掉的原地缩小淡出，数字跟着滚动。

### 2026-10-17 第五批

- **入口**：流转、文件、控制电脑（手机控制电脑）、搜索聊天记录都放进设备页（会话右上角"…"，页面标题是设备名），按设置页那种一行一行排；设备没连上时这些行变灰、写"连接后可用"。首页和桌面侧栏工具栏里的流转、文件入口去掉了。从设备页进流转，直接定位到这台设备。桌面会话顶栏只留音频共享、键鼠共享这类有开关状态的按钮和连接按钮。整体布局（三栏、设计语言）用户还在想，以后再改。
- **键盘**：
  - 百度这类输入法先在组字区里拼字，选词或收起键盘才提交；原来只转发提交的文字，组字区又看不见，所以"打字没反应"。现在请输入法对英文不做联想（字母直接提交），拼音组字时在画面顶部显示带下划线的组字条，收起键盘时组好的字照常发出（原来会被丢掉）。
  - 两端都记录"按键到画面"的时间：Mac 从收到按键到发出下一帧（实测 32–38 ms），手机从按键发出到下一帧解码显示，写进 window_stream.log，每 3 秒最多一条。
- **会话中途断掉**：手机尺寸一变（键盘、旋转、Aa）Mac 就重建虚拟屏，旧屏上的录屏流先于虚拟屏消失前没停，报"找不到显示器"，整个会话被当成窗口关闭。现在先停旧流再重建。
- **关闭应用**：最近任务里点 × 后，那个应用的窗口一起关闭；应用在手机上用别的方式关掉，2 秒一查、连续两次不在就关窗口。

### 2026-10-17 第六批

- **打字延迟**（实测）：Mac 从收到按键到发出新画面 10–60 ms；手机从按键发出到下一帧解码出来 17–88 ms（微信约 75 ms）。这一批：
  - Mac 编码器改用苹果为通话做的低延迟模式（Constrained High，编码优先速度），老系统退回原来的设置；
  - 手机解码器设成最高工作频率；
  - 切换窗口后的第一个按键，不再固定等 180 ms 让应用切到前台，改成一切过去就发（最多仍等 180 ms）。
- **横屏堆叠**：电脑窗口（宽卡片）收起时像时间机器那样往后往上叠，越往后越小、越暗，露出上沿；展开仍是一排。手机最近任务（竖卡片）不变。
- **文件管理器的拷贝不进聊天记录**：两端都把它当成剪贴板同步那类操作，传输时会话里不显示，完成后删掉那条聊天消息（文件不动）；失败的会出现在会话里，方便重试。以前拷过的记录不受影响。
- **Mac 应用图标**：流转页原来只给前 80 个应用要图标，Mac 装的应用一百多个、按名字排，微信这些排在后面的就一直没有。现在全部请求，仍然一次最多 4 个。

### 2026-10-17 第七批

- **堆叠**：时间机器式（越往后越窄）看起来像梯形，改成斜着叠：每张几乎一样大，往右上方错开，越往后越暗。
- **自动弹键盘**：Mac 端用辅助功能监听被流转应用的键盘焦点（TextFocusWatcher），焦点进入文本框、文本区、搜索框或网页里可编辑的地方时，经 `/window` 媒体通道发一个包（类型 5，标志位表示能否打字）给手机；手机的窗口任务据此弹出键盘，焦点离开时只收起它自己弹出的键盘（用户手动开关的不动）。Chrome、Electron 应用通过 AXManualAccessibility 打开网页内容的辅助功能树。焦点变化写进 window_stream.log。

### 2026-10-17 第八批

- **流转页背景**：去掉按设备颜色画的光晕，背景用 Whisper 其他页面同一个颜色。
- **最近任务**：
  - 堆叠：竖卡片（手机任务）也改成斜着叠。

### 2026-10-17 第十批

- **最近任务的堆叠和切换器是同一个布局**（FlowStack）：最前面的窗口，较新的在右，较早的往左塞在它下面。卡片位置用一条指数曲线算（右边那张离 0.95 个卡片宽，略压住前一张，不留缝；左边越往后越挤），页面上的堆叠就是这个布局缩小版；点开后每张卡片从它在堆叠里的位置长到切换器里，关上时缩回原处，页面上的堆叠在切换器开着时隐藏。

### 2026-10-17 第十六批：Windows、Linux、iOS

- **Windows 发送端**（`windows/capture/*`）：
  - 抓取和编码：WGC（无黄框、含弹出窗口）→ D3D11 视频处理器转 NV12（BT.709）→ Media Foundation 硬件 H.264（AMD，退路是微软软件编码），每个 IDR 前单独发参数集。
  - 后台运行：没有虚拟显示器驱动，窗口加上 `WS_EX_LAYERED | WS_EX_TRANSPARENT`，挪到某块显示器角落外只露一条缝。这样 DWM 继续合成，Chromium 和 WinUI 也继续绘制，屏幕上却看不见。位置记在 `staged.json`，崩溃后下次启动还原。
  - 输入：
    - 鼠标：消息发给 `RealChildWindowFromPoint` 找到的子控件；
    - 文字：以 `WM_CHAR` 发给键盘目标，绕开源端的输入法；
    - 快捷键：`AttachThreadInput` + `SetKeyboardState` + 同步发送 `WM_KEYDOWN/UP`；
    - 不依赖抢前台。
  - 管理员（更高完整性级别）的窗口不出现在目录里。
- **Windows 接收端**（`windows/receiver/*`）：
  - 硬件解码，D3D11 视频处理器输出到 flip 模型交换链（等待式，最大帧延迟 1）；浮层用 D2D 和 DirectWrite 画；退路是软件解码，再退是 GDI。
  - 悬停也发移动，带完整键码表，输入法候选窗跟随点击位置，RESIZED 带真实缩放比例。
- **Linux 发送端**（只支持 GNOME Wayland）：
  - 窗口：随包带一个 GNOME Shell 扩展 `whisper-window-stream@vireen.com`（D-Bus `com.vireen.Whisper.Shell1`，每次调用都核对调用方的可执行文件）。它负责列窗口、把窗口挪到虚拟屏和挪回、指针围栏，并通过 Clutter 虚拟设备注入键鼠，文字走 `Main.inputMethod.commit`。
  - 画面：Mutter `RecordVirtual` 建虚拟屏，排在真实显示器下方，不占键鼠共享用的左右边缘 → PipeWire（dlopen）→ 系统 libavcodec 里的 libx264。
  - 首次安装扩展要注销重新登录一次；KDE 和 X11 返回不支持。
- **Linux 接收端**：GTK3 + FFmpeg 软解，swscale 直接缩放到窗口像素；RESIZED、悬停、快照、输入法光标位置都补上了。

### 2026-10-18 第十七批：真机反馈修正、声音、安卓免 adb

- **关闭窗口**：
  - 主机收到 `closeWindow` 后观察窗口，用新的 `closeResult` 回报两种结果：
    - `closed`：窗口真的关掉了；
    - `open`：窗口还在，比如在问是否保存。判定依据有三种：目录里有 `modal` 标记、同一进程冒出了新窗口，或者超过 2.5 s 仍未关掉。
  - 窗口一直开着、之后才关掉时，再补发一次 `closed`。
  - 查看端：
    - 卡片在关闭期间变暗、转圈、不可点；
    - 刚关掉的窗口，在 6 s 内回来的列表里会被滤掉；
    - 窗口没关掉时提示，带"打开窗口"按钮。
- **"送到"**：对所有 Whisper 对端开放，不再只限 adb 连着的手机。电脑收到后直接打开窗口（`DesktopOfferOpener`），手机仍在岛上询问。
- **加载遮罩**（所有接收端统一规则）：
  - 稳定之前：显示上次画面或应用图标，加转圈。
  - 稳定的条件：最后一帧尺寸与 SIZE（或解码尺寸）一致、保持 300 ms，并且当前尺寸至少有 1 帧；首帧后 2.5 s 无论如何算稳定。
  - 稳定后用 180 ms 交叉淡化。
  - 恢复播放后 300 ms 内没有新帧，才再出转圈；"正在连接"的文字 8 s 后才出现。
- **窗口声音**：
  - 原生接口：`WSN_CAPTURE_AUDIO`（kind 11，PCM s16le，和视频同一时钟），以及 `wsn_capture_set_audio(capture, 0/1/2)`，2 表示本机静音。
  - 线路上：`typeAudioFormat=6`、`typeAudio=7`，只发给在 `open` 里带了 `"audio": true` 的查看端。
  - 编解码：主机用 Opus 20 ms 一帧，编不了时退回 PCM；查看端在流 isolate 里解码（`WorkerOpus`）。
  - 同一查看端看同一应用的多个窗口时，只有一个窗口带声音；它关掉后，由下一个接上。
  - 各平台采集与本机静音：
    - macOS：14.2 及以上用 Core Audio 进程 tap，能本机静音，需要"录制系统音频"权限；更早的系统用 ScreenCaptureKit，本机仍会出声。
    - Linux：PipeWire 私有 null-sink，能本机静音，停止或崩溃后恢复原来的路由。
    - Windows：进程环回采集。静音会让采集也变成静音，所以本机无法静音，要做就得装虚拟声卡驱动。
  - 播放：
    - Windows：WASAPI；
    - Linux：PulseAudio；
    - 手机：AudioTrack（安卓）、AVAudioEngine（iOS）。
    - 都有约 70 ms 的抖动缓冲，并按 pts 处理跳变和时钟漂移。
- **Mac 来源推错窗口（隐私）**：
  - 原因：被挪上虚拟屏的窗口，原来是按"整块虚拟屏"来抓的。系统把别的应用的窗口恢复到这块屏上时，那个窗口也会被推流。
  - 改法：只用两种过滤器，并且对不上就拒绝：
    - 原地抓时，只抓这一个窗口；
    - 上了虚拟屏时，只抓虚拟屏上本应用的窗口，并排除它其他的普通窗口；另有观察器盯着新出现的窗口。
  - 上虚拟屏时不再等满 3 s 的 HiDPI 模式。
- **Windows 资源管理器**：
  - 问题：它的命令栏、地址栏、搜索框是 WinUI/XAML 内容，不吃投递的鼠标消息。
  - 改法：落在这类内容上的点击改用 UI Automation 按到最小的可操作元素；UWP 的文本框短暂切到前台再发真实按键。
  - 它们弹出的菜单挪到被抓的窗口上，查看端能看到、能点。
- **安卓免 adb**：
  - 手机本身成为 protocol 12 来源。主机通过 `WindowCaptureBackend` 接缝，换成 `PhoneCaptureBackend`。
  - agent 改成常驻进程：`--daemon`，单实例，断开 adb 后继续运行。
  - 手机 App 通过本机回环 TCP 连 agent，两道校验：uid 必须一致，并用 HMAC 做挑战应答（WAG2）。
  - agent 没在运行时，手机回 `agentNotRunning`，电脑显示引导。
  - 手机设置里新增"窗口流转服务"页。
  - 手机自己用无线调试启动 agent：还没做完。
    - 已完成：SPAKE2 用 libsodium 实现，并和 BoringSSL 互通验证过。
    - 还没做：TLS 配对、adb connect、界面。
    - 在做完之前，入口隐藏（`SELF_START_AVAILABLE=false`），目前仍需有 adb 的电脑启动一次。
- **反向拨号**：
  - 场景：手机开着 VPN 或在 NAT 后面，电脑连不进去。
  - 条件：查看端在 `open` 里带 `dialBack`；主机是手机或平板；并且主机是这条 Whisper 会话的客户端。三条都满足时，主机在 `accept` 里写 `hostDials`。
  - 流程：查看端签发一次性 token，用 `dial` 发给主机；主机拨查看端的 10002 端口 `/window`。
  - 安全：密钥方向与证明方式都不变。
  - 电脑之间不反向。
- **手机当摄像头和麦克风**：暂停。方案、各平台结论、半成品存档在分支 `wip/phone-camera`。

### 2026-10-18 第十八批：窗口大小、Linux 声音、音量、一个窗口只在一处

- **Linux 接收端没声音**：
  - 原因：opus_codec_linux 3.0.5 发布的 libopus 是 0 字节的空文件。插件发现打不开就退回系统的 `libopus.so.0`；流转的解码线程却只要文件存在就直接打开，打开失败，所有声音包都被丢掉。
  - 修正：`WorkerOpus.openFirst` 依次尝试解出来的副本、`libopus.so.0`、`libopus.so`。
  - 原生放音已单独验证：用私有空 sink 录到的 RMS 为 3224，符合预期。
- **查看端的像素密度**：
  - 查看端在 `open` 和 `viewport` 里带上 `pixelRatio`，即每点几个像素。
  - 主机通过 `captureSetPixelRatio` 转给捕获端，C ABI 是可选符号 `wsn_capture_set_pixel_ratio`。
  - Mac 主机按"窗口点数 × 查看端像素密度"出图，上限 2，没收到时仍按 2。之前 Mac 一律按 2 倍出图，1 倍屏的 Linux 解不过来，只有 3 帧。
- **安卓窗口的大小**：
  - 手机主机：
    - 目录里的窗口按手机屏幕竖着的点数报宽高，另附 `screen`，桌面窗口因此按手机的形状打开；
    - 虚拟屏像素 = 窗口点数 × 查看端像素密度，最大不超过手机自己的屏幕；
    - dpi 让应用的排版和手机上一样（手机短边的 dp 对应窗口短边）；
    - 之后改窗口大小时 dpi 不变（agent 改不了），窗口变大就多显示内容，字不会变大。
  - adb 来源（Mac 上用 USB 连着的手机）：窗口第一次和画面同形状时，记下"每点几个像素"和最长边；之后改窗口大小，虚拟屏按这个比例跟着变，同样不超过最长边。
- **自由调整窗口大小**：
  - 新的创建标志 `WSN_FLAG_REFLOW`：会跟着窗口重新排版的来源（Whisper 对端、能重排的安卓来源）不再锁定宽高比，画面在对端跟上之前留黑边。
  - 改完约 2 秒后，画面形状如果还对不上，窗口收拢到画面的形状。
  - 不带这个标志时行为不变。
- **音量**：
  - 每个桌面窗口有自己的音量控制，只在有声音时出现：
    - Mac：标题栏的扬声器按钮，弹出滑块；
    - Windows：窗口角上的按钮；
    - Linux：标题栏的音量按钮。
  - 原生调整增益时有约 20 ms 的渐变，不会爆音。
  - C ABI：`wsn_surface_set_volume`、`WSN_WINDOW_VOLUME` 事件，以及 `wsn_set_strings`（窗口自己显示的文字）。
  - Dart 按"设备 + 应用"记住音量，下次打开时恢复。
  - 手机和平板交给系统音量键。
- **一个窗口只在一处**：
  - 主机目录里，正在流转的窗口带上 `viewer`（对方的 peer id）和 `viewerName`。
  - 另一台设备打开同一个窗口时，主机结束旧的流，原因是 `movedAway`；旧窗口提示"已在另一台设备上打开"，2.5 秒后关闭。
  - 同一台设备再次打开时，只替换自己的流，和以前一样。
  - 查看端按设备 id 判断窗口是否已经打开，不再看来源对象是不是同一个；"送到"和流转空间里点卡片，都会把已经打开的窗口调到前面。
  - 流转空间的卡片会标出"正在 X 上显示"。
- **扩展屏和镜像屏**：没有开始做。镜像屏是抓整块屏，四个平台都能复用现有链路；扩展屏在 Mac 和 GNOME 上可以复用虚拟屏，Windows 需要签名过的虚拟显示器驱动，所以做不了。
- **实测**：
  - Windows → Linux 的声音：录 Linux 的输出 4 秒，是 522 Hz 的测试音，没有一个 10 ms 的空段。
  - 一个窗口只在一处：Linux 正在看时 Mac2 打开同一个窗口，Linux 那边以 `movedAway` 结束，Mac2 接手。
  - 从 Windows 当接收方那条连接取 512 MB 文件到 Linux，sha256 一致。
  - 音量控制和自由缩放：Windows、Linux 用测试程序验证过；Mac 只做了编译检查。
  - 手机窗口的尺寸：一加当时锁屏，没有在真机上验证。

## 安全与隐私

- **安卓经 adb 流转也要求已配对、已信任（2026-10-17 用户要求，已实现）：** 电脑先通过 adb 读手机 Whisper 报告的设备 ID 和身份公钥，和本机数据库里已信任设备的记录对上才拉起 agent。手机没装、没打开过 Whisper 或没配对时显示"未配对"和怎么做。

### 2026-10-19 第十九批：桌面最近任务、卡顿、画质、Mac 权限

- 这台手机的 H.264 硬件编码器标注最多 16 路，总吞吐 3,916,800 块/秒。
- 虚拟屏带系统装饰时会出现状态栏，并额外启动一个桌面任务；whisper-agent 默认不带系统装饰。
- 用 `--start-app` 打开已经在运行的应用时，旧任务会随虚拟屏一起被销毁，进度丢失。所以 whisper-agent 一律用"挪任务"打开已在运行的应用，并且永远不带"销毁内容"标记。

## P0 结果：合盖实测（2026-10-16，已否掉"合盖装包"场景）

- **设备和方法**：MacBook Air M4，`pmset -a disablesleep 1`。用临时程序以 ScreenCaptureKit 抓自己的窗口（AppKit 时钟加 WebKit 动画），每秒记录一次状态。
- **只靠系统能力**：
  - 合盖那一秒，可用显示器从 1 个变成 0 个，并且立即锁屏（没有等锁屏策略里的 5 分钟）；
  - 合盖 18 分钟，0 帧。
- **加上虚拟屏，接着电源**：
  - 合盖后虚拟屏仍然在工作，没有立即锁屏；
  - 但窗口立刻被系统标成"不可见"，约 10 分钟里基本是 0 帧；
  - 到"10 分钟后关闭显示器"的时间点，虚拟屏也睡了，随后锁屏。
- **开盖时**：窗口完全被挡住会 0 帧；放到虚拟屏上，用户正常用主屏时稳定在约 29 帧。这个结果用在"Mac 被挡住的窗口"那一节。

## Decisions（2026-10-16）

1. 不做"笔记本合盖装包"这个场景（见上方实测）。
2. 范围：安卓 ↔ 电脑、电脑 → 手机和平板、电脑 → 电脑；不做安卓 → iOS；iOS 只做接收端。
3. 顺序：先做安卓 → Mac，再做 Mac → 安卓和 iPad，然后是 Windows、Linux、电脑 → 电脑。
4. 安卓来源用基于 scrcpy-server 改写的 whisper-agent，原样的 scrcpy-server 留作兜底；不用 Shizuku。
5. Mac 被挡住的窗口用私有虚拟屏解决，失效时退回原地流转。
6. 已信任的设备直接允许查看和控制窗口。
7. 安卓来源的声音在 P2 和画面一起做；Mac 来源的声音放到后面，复用音频共享。
8. "手机解锁电脑"作为另一个独立功能考虑：Windows 现有的锁屏服务能往锁屏界面输入；Mac 上能不能做要单独实测。
9. 用户确认的核心场景（2026-10-16）：浏览手机应用（最近任务做成堆叠卡片），点开后流转到桌面窗口、手机上留在后台，可同时开多个窗口、随时暂停，声音跟过来；能看 UI 树、跑简单自动化规则，以后接 AI。
10. 暂停只停画面；声音由窗口上的静音按钮单独控制。关闭窗口时应用回到手机后台。
11. Dart 直接讲 adb 服务协议，和 Android Studio 共用 5037 上的服务；正式包是否随带 adb 等许可确认后再定。
12. 原生代码放在纯 FFI 插件 `packages/window_stream_native`（不设 `pluginClass`），以后各平台的实现都放在里面。
