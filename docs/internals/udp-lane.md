# 键鼠和声音的 UDP 通道

键鼠共享和系统声音共享除了原来的 WebSocket，还各有一条加密的 UDP 通道。Wi-Fi 上丢包时，这条通道不会让后面的包排队等重传。本文说明它怎么建立、各自怎么用，以及哪些情况会退回 WebSocket。实测数据见 [2026-11-10 的记录](../records/2026-11-10-udp-weak-wifi.md)。

## 为什么

TCP 丢了一个包，后面已经到的包也要等它重传，通常要等几百毫秒。在 1%–4% 丢包的 Wi-Fi 上，指针会停住再跳，声音会断。键鼠和声音都不怕丢掉单个包：下一个移动包会告诉对方指针到了哪里，丢掉的一帧声音也可以补出来。它们怕的是排队等待。

## 建立

两种用途共用一套格式和密钥派生，见 `lib/socket/datagram_seal.dart` 和 `lib/socket/datagram_endpoint.dart`。

- **密钥**：WebSocket 认证之后，两端已经共有媒体密钥和这次连接的一次性升级令牌（channel binding）。用 HMAC-SHA256 从这两者、用途（`remote-input` 或 `audio-group`）和会话号派生出两个方向各自的密钥和 8 字节通道号，所以两端不会在同一个密钥下重复使用 nonce。
- **格式**：`WUD1` | 通道号 (8) | 序号 (8，大端) | 认证标签 (16) | 密文。用 XChaCha20-Poly1305 加密，nonce 由序号构成，头部计入附加数据。明文第一个字节是类型：0 是保活，1 是数据。载荷最多 1400 字节，局域网里不会分片。
- **防重放**：每个方向记住最新序号往前 1024 个，重复的和更早的都丢掉。只有通过认证的包才会移动这个窗口。
- **一个端口**：每个 isolate 只开一个 UDP 端口，收到的包先按明文里的通道号分给对应的会话，再由那个会话检查真伪。
- **键鼠**：发起方的 offer 带 `datagrams: 1`，接收方的 accept 带 `datagramPort`（接收方 UDP 端口，随机分配）。
- **声音**：接收端在和媒体端口同号的 UDP 端口上监听，发送端已经从 accept 里拿到了这个端口号，所以协议里没有加新字段。
- **地址**：拨号的一方从 WebSocket 地址知道对方在哪；应答的一方从第一个真包的来源学到地址，此后每次都回给最新来源。只支持 IPv4。

## 保活和退回

- 两端每 250 ms 发一个保活包。1 秒内收到过对方的包，通道就算可用；不可用时，所有数据都走 WebSocket。
- 收数据的一端在数据进来时，至少每 40 ms 回一个保活包。只收不发的笔记本，Wi-Fi 网卡会在两个信标之间打盹，路由器就把发给它的包攒到它醒来，每次能晚两三百毫秒。走 TCP 时，回的 ACK 让网卡一直醒着。2026-11-10 在小新上测到过这个问题，`test/datagram_lane_test.dart` 有对应的回归测试。
- 发出的 UDP 包标成交互语音的优先级：macOS 设 `SO_NET_SERVICE_TYPE` 为 VO，Linux 和 Android 设 DSCP 46。Windows 没有组策略时会忽略这个标记，不影响使用。

## 键鼠

见 `lib/remote_input/remote_input_lane.dart` 和 `remote_input_datagrams.dart`。只有跨屏的键鼠共享（`edgeTraversal`）用 UDP，手机控制电脑仍走 WebSocket。

- 每个包都带两个值：`travel` 是这次会话里指针累计移动的距离，`fence` 是它之前最后一个不能丢的事件的序号。不能丢的事件是按键、鼠标按钮、滚轮、进入和离开。
- **移动只走 UDP。** 停下后 16 ms 再补发最后一个包。丢了也没关系，接收端用下一个包的 `travel` 减去已经移动的距离，算出该移多少。
- **不能丢的事件两条路都走。** WebSocket 发一份；UDP 在 0、8、24 ms 各发一份。接收端收到哪份先用哪份，后来的重复包丢掉。
- **顺序。** 接收端按 `fence` 的顺序执行不能丢的事件。移动包要等它的 `fence` 到了才执行，所以拖动不会在按钮按下之前开始。执行不能丢的事件之前，接收端会先把指针补到那一刻的位置。
- 不带 `travel` 的包（来自旧版本发送端）原样执行。
- 会话结束时，两端各在日志里写一行 `remote_input_lane`：几成走了 UDP、哪条路先到、移动包等待时间的分位数。

## 声音

见 `lib/audio/audio_group_lane.dart`、`audio_packet_gaps.dart` 和 `audio_media_isolate.dart`。只有电脑之间用：UDP 接在桌面的音频 isolate 里，Android 播放走另一条路，仍用 WebSocket。

- 每个 UDP 包带两帧：这一帧和上一帧，先旧后新，各自前面写 16 位长度。丢一个包，下一个包里还有这一帧。
- 接收端按帧序号只播一次，重复的丢掉。缺 1 到 3 帧时，用 Opus 的丢包补偿补出来；缺得更多就留空，不去猜。序号突然倒退很多，当作发送端重新开始计数。
- 没有用 Opus 自带的前向纠错：128 kbps 的音乐走的是 CELT 模式，这种模式下前向纠错基本不起作用。
- 声音停止时，接收端在日志里写一行 `playbackClosed`，包括播放帧数、补出的帧数、重复帧数、留空帧数和迟到帧数。

## 和文件传输一起

UDP 解决的是丢包后的排队，解决不了链路本身被占满。同时传大文件时，文件的 TCP 数据会把 Wi-Fi 的队列塞满，UDP 包也得在后面排队。所以有声音或键鼠时，传输限速（`lib/socket/transfer_pacer.dart`）量出链路能跑多少，只用九成，并且把数据切成 10 毫秒一片均匀地发，链路不会连续被占满。量链路和隔一阵探链路的那几秒仍会跑满。做法和实测见 [留一成带宽](../records/2026-11-12-transfer-pacing-headroom.md)和[切成小片](../records/2026-11-12-transfer-pacing-slices.md)两条记录。

指针在动时（两秒内有键鼠事件经过本机）不去探链路能不能跑得更快，等它停下再探。传文件时指针卡，看日志里的 `transfer_pacing` 和带 `running` 的 `remote_input_lane`，各字段的意思见[这条记录](../records/2026-11-12-transfer-pacing-pointer-busy.md)。

在途的未确认数据不能压得太小：2026-11-08 试过压到四分之一秒的量，接收端最慢每秒才确认一次，额度越小测出的速率越低，额度又跟着变小，最后降到每秒几十 KB，见[记录](../records/2026-11-10-udp-weak-wifi.md)。按估出的链路速度长期压着也不行，会自己往下掉；现在只在放开限速的那一刻收回到两秒的量。

## 和旧版本

不用改协议版本。

- 旧版本的接收端不认识 `datagrams` 字段，会忽略它；它的 accept 不带 `datagramPort`，新版发送端就全走 WebSocket，包也不加 `travel` 和 `fence`。
- 旧版本的声音接收端不监听 UDP，不会回保活，通道一直不可用，声音照旧走 WebSocket。
- 旧版本的发送端不会发起 UDP，新版接收端只是多开了一个用不上的端口。

## 防火墙

Windows 第一次运行时弹出的防火墙询问，会给 `whisper.exe` 同时放行 TCP 和 UDP。如果 UDP 被单独挡住，通道一直不可用，所有数据退回 WebSocket，功能照常，只是在弱网下又会卡。日志里 `remote_input_lane` 的 `viaLane` 一直是 0，就是这种情况。

## 测试

- `test/datagram_lane_test.dart`：格式、篡改、错投、重放窗口，真实 UDP 套接字上的通道，以及收数据时的回包。
- `test/remote_input_lane_test.dart`：丢包、乱序、只有 WebSocket 先到等情况下，接收端执行的结果和只走 WebSocket 时一样；还有一条真实套接字的端到端测试，以及和旧版本的协商。
- `test/audio_group_lane_test.dart`：两帧打包和拆包，以及去重、补帧和留空的规则。

## 没有验证的

- Linux 没有在真机上测过 UDP 通道。
- Android 播放声音不经过音频 isolate，没有接 UDP，仍全走 WebSocket；电脑发给手机的声音在弱网下和以前一样。
- 只在一台 Mac 和一台 Windows 之间、同一个 2.4 GHz Wi-Fi 上测过。没有测过两端都是 Windows 的情况，也没有测过有线网络。
- 测试时的输入是程序生成的移动和点击，不是人手操作，手感还要人试。
- IPv6 地址的连接不建 UDP 通道，全走 WebSocket。
