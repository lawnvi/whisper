# 弱 Wi-Fi 上的 UDP 键鼠和声音

2026-11-08 至 11-10，在一台 Mac（调试版）和一台 Windows 笔记本（小新，Release 版测试副本）之间，比较键鼠和声音走 UDP 和走 WebSocket（TCP）的差别。做法和现在的代码见 [UDP 通道](../internals/udp-lane.md)。

## 环境

| 日期 | Mac | Windows | 空闲时 ping |
| --- | --- | --- | --- |
| 11-08 | 802.11n，2.4 GHz 第 4 信道，-68 dBm，发送速率约 14 Mbps | Intel AX211 | 7–24 ms，丢包 0–4% |
| 11-10 | 802.11n，2.4 GHz 第 11 信道，-51 dBm，发送速率 144 Mbps | 同上，接电源 | 平均 6 ms，不丢包 |

两台都连同一个路由器。11-10 的网络比 11-08 好很多，没有找到 11-08 那样稳定丢包的环境。

输入都是程序生成的：每 8 ms 一个移动包，约每秒一次按键。声音是 Mac 播放的 440 Hz 正弦波，每轮约 60 秒，Opus 128 kbps，20 ms 一帧。

## 键鼠（11-08）

每轮一分钟，统计接收端移动包的等待时间（从收到到执行）：

| 方式 | p50 | p95 | p99 | 最大 |
| --- | ---: | ---: | ---: | ---: |
| UDP | 13 | 32 | 34 | 71 |
| TCP | 18 | 231 | 1118 | 1722 |
| UDP | 14 | 172 | 540 | 653 |
| TCP | 17 | 34 | 50 | 109 |
| UDP | 13 | 36 | 103 | 287 |

单位 ms。同一种方式前后两轮能差十倍，靠分轮统计下不了结论。于是改成同一轮里每个移动包两条路各发一份，比较同一个包哪份先到：

- 空闲时约 6000 对，UDP 先到 77%。TCP 晚到的那些，p95 晚 107 ms，最长晚 700 ms。这段时间 ping 平均 78 ms，最长 693 ms，丢包 1.7%。
- 同时传一个 20 MiB 文件时，TCP p95 晚 304 ms，最长晚 1253 ms。UDP 自己的等待 p95 也有 413 ms：文件把 Wi-Fi 的队列塞满了，UDP 包也在排队。
- 两台之间 UDP 一直可用：空闲的几轮里 5969 个移动包全走 UDP，Windows 防火墙放行了测试副本的 UDP。

11-10 改了收端回包之后，又跑了一轮 30 秒。这轮大部分输入按布局走到了别的设备（见下面的教训），测试副本只收到 126 个：125 个走 UDP，1 个走 WebSocket，等待 p50 2 ms、p95 7 ms、最大 12 ms。

## 声音（11-10）

接收端每轮结束时记一行：播放帧数、补出的帧数、留空帧数和迟到帧数。

| 方式 | 迟到帧 | 补帧 | 这轮 ping 最长 |
| --- | ---: | ---: | ---: |
| TCP | 0 | 0 | 77 ms |
| TCP | 0 | 0 | 28 ms |
| TCP | 11 | 0 | 290 ms |
| UDP，收端只回保活 | 16 | 3 | 285 ms |
| UDP，收端只回保活 | 22 | 0 | 227 ms |
| UDP，小新另外每 20 ms 发一个包 | 0 | 0 | 26 ms |
| UDP，收端每 40 ms 回一次 | 14 | 0 | 64 ms |
| UDP，收端每 40 ms 回一次 | 0 | 0 | 57 ms |

每轮约 3030 帧。网络好的时候 TCP 也很少卡，两者差不多。

同时传 16 个 20 MiB 文件时（接收端每台设备最多排 11 个，多出的 5 个被拒收，这是测试的问题）：

| 方式 | 结果 |
| --- | --- |
| TCP | 声音中途断了一次，重连后才接上，少播约 20 秒；迟到 74 帧 |
| UDP | 一直没断：留空 74 帧（约 1.5 秒，分散在整轮里），补帧 28，迟到 20 |
| UDP | 一直没断：留空 0，补帧 0，迟到 83 |

## 找到的问题

**只收不发的网卡会打盹。** 早期的 UDP 每轮都有十几二十个迟到帧，而且这几轮 ping 也有两三百毫秒的尖峰；TCP 那几轮没有。让小新另外每 20 ms 发一个小包，迟到和尖峰就都没了。原因是小新只收不发时 Wi-Fi 网卡进入省电，路由器把发给它的包攒到它醒来；走 TCP 时它要回 ACK，网卡就一直醒着。修法是收端在数据进来时至少每 40 ms 回一个保活包。修了之后，空闲的两轮里没有再出现两百毫秒以上的 ping 尖峰；还剩的迟到帧 TCP 也有，是链路本身的抖动。

**停声音时偶尔断掉整条连接。** 一边传文件一边停声音，Mac 把连接断了，正在传的文件全部转入等待重连。原因是停止消息和小新发出的延迟报告在路上交叉：报告到达时，Mac 已经忘了这个会话，就把它当成非法消息。传文件时消息排队更久，所以更容易碰上。这个问题和 UDP 无关。修法是对已结束会话的迟到报告直接忽略，和停止消息已有的处理一样。修了以后，三轮"声音 + 传文件"都没有再断。

**传输在途数据压到四分之一秒的量，会越缩越小。** 11-08 为了让指针少排队，试过在有实时流量时把传输的在途数据压到四分之一秒的量。11-10 实测发现，放声音时文件传输只有约 57 KB/s：接收端的数据不够一个确认间隔时，最慢每秒才回一次确认，在途额度越小，测出的速率越低，额度又跟着变小。这个改动没有采用。改回原来的限速后，放声音时传输约 0.3–1.2 MB/s，停了以后约 2.3 MB/s（小新接收时单核占满，一直就是这个速度）。

## 测试方法上的教训

- 分轮统计的差别比两种方式之间的差别还大。比较两条路，要在同一轮里让同一个包两条路各走一份。
- 合成输入按键鼠布局走：布局里还有别的在线设备时，指针会移过去。只在布局里只有测试设备的时候跑。
- 刚启动的 App 里，音频 isolate 要等第一次放声音才创建。在它之前改它的变量不会生效，要先确认改到了。

## 没有测的

- Linux 和 Android。
- 两台都是 Windows，或者有线网络。
- 真正丢包严重的 Wi-Fi（11-08 那种）下的声音对比。
- 人手操作时的手感。
