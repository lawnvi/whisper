# 2026-11-14 共享的目录和锁屏服务自更新的攻防

接着 [提权专项审计](2026-11-13-privilege-escalation-audit.md) 做的第三轮，只看那之后新加的两块：电脑「共享的目录」（已配对、允许浏览或修改的设备能不能碰到排除的、系统的和底线里的东西）和 Windows 锁屏服务的自更新（同一用户下的普通程序能不能借它拿到 SYSTEM，或者让它坏掉）。两路只读找问题，每条我先复现再修。

改动跑过 `flutter analyze` 和完整的 `flutter test`。

## 已修

| 级别 | 问题 | 验证 |
|---|---|---|
| 中高 | 排除的目录、底线里的地方（数据库、别的设备挂在这里的文件夹）都按路径认，可对方能改名、移走、删除装着它们的上层目录：把 `~/Documents/X` 改名，排除的 `X/Private` 就脱离了规则；Linux 和 Windows 上把文稿改名就能读到数据库；删上层会连排除的内容一起删掉。现在「修改」类操作（写、改名、移动两头、删除、放进回收站）遇到装着排除目录、底线、Whisper 自己的文件或挂载的文件夹一律拒绝（`FsSharePolicy.allows` 的 `change`，`FsProtectedAreas.holdsAny`） | 测试修前能改名、修后拒绝；Linux、Windows 的数据库位置没在真机上试 |
| 中 | `.git/worktrees/<名字>/commondir` 决定工作树从哪里读 config，对方能改写它，指到自己放的一份带 `core.fsmonitor` 的 config，编辑器打开那个工作树跑 `git status` 时就执行命令。`commondir` 和 `config` 一样只能看不能改 | 测试修前能改、修后拒绝 |
| 中 | 发布流程在手动触发、不发布的测试运行里也给锁屏服务的清单签名，版本可以是任意值或 `0.0.<运行号>`；运行的产物谁都能下载，签过的清单不过期，服务收任何更高的版本，同一用户的程序就能把测试构建装进服务，或者用一个很大的版本号让它以后拒收正式更新。现在只在推标签或勾了发布（两者都核对过 pubspec 的版本）时签，测试运行的安装包不带清单 | 工作流的源码检查；没有真跑 CI |
| 低 | 服务换文件时，`.new` 写完就关了，挪开的旧文件也没握着；普通用户能打开 Program Files 里的文件，不共享删除权地占着它们就能让改名失败，回退时再占住旧文件，服务的 exe 就没了，之后应用的修复会让管理员授权运行用户可写目录里的 `whisper.exe`。现在 `.new` 从创建到换进去都独占，旧文件挪开前先拿到删除权并一直握着，改名都按句柄做（`FileRenameInfo`），回退时先把新文件挪开再放回旧的 | 小新上 MSVC `/W4 /WX` 编过，压力测试见下面 |
| 低 | 读文件时先检查、后打开，中间有空隙：共享的目录里如果本来就有一个指向底线的符号链接（列表里藏着，但知道名字就能动），允许修改的设备能在这个空隙里把它改名到要读的文件的位置上，读到的就是链接指向的东西。现在指向不共享地方（或者哪儿也不指）的链接，对方不能改名、移动或删除（`FsPathResolver.checkChange`）。还剩一个变种：整个文件夹对调，同样要求那种链接本来就在，没有处理 | 测试修前能改名、修后拒绝 |
| 低 | Linux 把分区挂在主目录里（`~/data`）时，设置里它是一块单独的盘，开关默认关，却照样随主目录共享。现在关着的盘挂在共享的目录里也算排除 | 测试修前能读、修后拒绝；Linux 真机没试 |

## 压力测试（锁屏服务换文件）

在小新（Windows 11）上把新旧两版 `input_service_update.cpp` 各编进一个测试程序：临时目录里放一个正在运行的 exe 和一个 dll，连续换 300 次，4 个线程同时不停地以不共享删除权的方式打开目录里的文件。每次换完核对两个文件都在、要么全新要么全旧。

| 攻击 | 旧版 | 新版 |
|---|---|---|
| 没有 | 300 次全成功 | 300 次全成功 |
| 只占 `.new` 和挪开的 `.old` | 成功 4 次，296 次失败 | 300 次全成功 |
| 连目标文件一起占 | 300 次全失败（干净地放弃） | 300 次全失败（干净地放弃） |

三种情况下两版都没有出现文件丢失或新旧混杂。旧版丢 exe 要在回退的瞬间抢到挪开的旧文件，300 次里没抢到，所以这一条没有复现；复现了的是旧版很容易被拦住更新，新版不会。按句柄改名（包括挪开正在运行的 exe）在真机上可用。没有在真的服务里跑过一次更新。

## 看过、成立的

- 共享的目录：macOS 上换大小写和 NFC/NFD 绕不过去（realpath 返回磁盘上的写法，比较前都折叠大小写）；Windows 的结尾点和空格、`:`、备用数据流、设备名、盘符和 `\\?\` 前缀过不了路径检查，短名在已有条目上按真实路径重查；文件夹发送的扫描不跟随链接，留下 Whisper 的文件；列表里的链接按目标判断；往 `.git` 里新建、改名进去都被挡住；拷进来的文件落地前重新解析目标。安卓没有这套规则，按设计和数据线看到的一样。
- 锁屏服务：校验的就是写进去的那份内容（读进内存、算哈希、写同一块）；按客户端身份读，读完才以 SYSTEM 写；清单里只认四个固定的名字；清单解析、版本比较、和更新包签名的区分都对；Program Files 里的目录和注册表项普通用户写不了；管道只给本会话的用户，客户端核对管道属主是 SYSTEM；构建作业拿不到签名密钥。

## 决定不修

- 任何更高版本的已签名构建都会被服务接受，同一用户的程序能挑一个预览版装到正式版用户的服务里。装进去的也是自己发布、签过名的代码，下一个正式版又会换回来；要分开得在清单里加渠道，不值得。
- 服务为更新重启时，别的进程能抢先建同名管道，只会让服务起不来（应用核对管道属主，不会连上假的）。能做到的程序本来就在用户的账户里，管道名又必须让用户自己的程序知道，没有真正的解法。
