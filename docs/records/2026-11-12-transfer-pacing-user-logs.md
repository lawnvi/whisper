# 用户贴的日志：传文件时指针卡在哪

2026-11-12。接着[上一条](2026-11-12-transfer-pacing-pointer-busy.md)。用户用 `3171ac1` 的构建在两台 Windows 上试：控制端同时发文件，被控端收文件，传了两次约 1 GB，期间一直晃鼠标。两边的 `transfer_pacing` 和 `remote_input_lane` 行都贴回来了。下面的时间是用户机器上的时间。

## 第二次传输的经过

被控端「多等」是比这次会话最快的一次多花的毫秒数。

第一次（16:44）的前十秒一样：`measuring` 时 p50 46 ms，转成 `held` 后 26–33 ms。

## 读出来的

- **控制端没有问题。** 采集到发出 0–1 ms，主线程最多晚 13 ms；限速按估的链路九成走，每秒约 105 片，发送定时器最多晚 6–16 ms。
- **UDP 是通的。** 被控端收到的移动九成八以上走 UDP。
- **每次传输开头都没有限速。** 第二次开始时第一次量到的链路速度（41 MB/s）还记着，第一行却是 `measuring`。点「发送」时指针在控制端自己的屏幕上，键鼠共享处于等待（`armed`），不算有实时流量，传输不限速并开始数链路；指针过去以后要等两次计数数完（约 5 秒）才限住。这几秒被控端 p50 多等 46–102 ms，是掉帧最明显的一段。
- **限住之后还要十几秒才缓过来。** 从不限速转为限速时，先按估的链路一半跑 1.5 秒让积压排空。积压如果在 Wi-Fi 的队列里，这 1.5 秒足够排空几百毫秒的量；p50 却用了约 15 秒才从 56 降到 16 ms，积压更像在别处，比如被控端收文件的那条处理。这次的数据分不清。
- **稳住以后九成基本够。** p50 比不传时多 6–8 ms，p95 和不传时的波动差不多。
- **传完以后被控端主线程四次卡约半秒。** 这段时间指针最长等 0.55 秒，比传输中还差，和网络无关。原因没查到。如果收的是视频，嫌疑是生成缩略图：Windows 上用的是 media_kit（libmpv），加载库、`mpv_create` 和 `mpv_initialize`、`dispose` 五秒后的 `mpv_terminate_destroy` 都在主线程上同步执行。

## 量法的两个问题

- **`loopLagMs` 看不到一直落后的事件循环。** 原来用周期定时器量相邻两次触发的间隔。Dart 的周期定时器按最初的时刻表排，事件循环一直落后时，触发间隔照样均匀，读数只反映落后的变化。改成每次触发后重新设一个一次性定时器，量它比该触发的时刻晚了多少。本机试验：另一个 isolate 约每 12.7 ms 发一条消息，每条处理 16 ms，消息最多等了 344 ms，新量法读到 286 ms；处理 5 或 9 ms、不积压时读到 7–10 ms。在 Windows 上，没有积压也会读到 16 ms 左右，是定时器的精度。
- **「多等」的基线会漂。** 两台用各自的墙上时钟，五分钟里不传文件时的 p50 从 3 漂到 9–10 ms。比较时要和附近不传文件的时段比。

## 改动

- **开着键鼠共享就算有实时流量**，指针不在对面也算：指针随时会过去，过去时链路不能是满的。链路速度已知时，传输一开始就限着。
- **记住的链路速度只给同一台设备用。** 记五分钟，原来不分设备。键鼠共享常开以后，传给手机之后马上传给台式机，会按手机的链路限着，要等探链路才发现。
- `loopLagMs` 换成上面的量法。

## 没有测的

- 真机。三处改动都只在仿真和单元测试里跑过。
- 传完以后那几次半秒卡顿的原因，要知道收的是什么文件，以及被控端那段时间日志里的其他行。
- 限住之后慢慢缓过来的十几秒，积压在哪里。下一次的 `loopLagMs` 能说明是不是在被控端的事件循环里。
- 开着共享、链路速度还不知道（五分钟内没传过给这台设备）时，头几秒照旧不限速。
