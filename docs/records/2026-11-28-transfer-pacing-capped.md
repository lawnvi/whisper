# 2026-11-28 拿不到排队时间时的限速：计数做法换成"按链路的一半"

J8 第 4 步（见 [协商稿](2026-11-27-network-architecture-consensus.md)）。门禁是：先在 `test/transfer_pacer_test.dart` 的模拟链路上跑过，包括每 1.7 秒减半的那条，再在弱 Wi-Fi 上实测一次。本文是模拟部分，弱 Wi-Fi 实测还没做。

## 做法

有键鼠或声音、但对方回答不了时间戳时（手机走 WebSocket 播放声音、UDP 被防火墙挡住、反拨的连接），以前用一套按确认数估链路的计数做法，有量链路、重量、探、排空、放开几种状态。现在换成：

- 开头不限速，数两轮（每轮 2 秒）到了多少，算出链路能跑多少，之后按一半发。
- 连续两轮到的比发的少一成以上，就降到实际到达量的一半，最低不低于量到值的四分之一。
- 不往上探；换设备或闲置五分钟后重新量。
- 是否切 10 ms 小片按链路速度判断，不按限速后的速度。

能拿到排队时间时照旧按排队调速（`steered`），没有改。

## 模拟结果

同一套模拟（`_transfer`，模拟时钟，和机器无关）。"速度"是后半段每秒到达的字节数；"p95"和"最坏"是后半段任意时刻实时内容要在文件数据后面等多久。旧做法那一列的空格，是旧做法在新测试的第一个断言就失败了，那个场景没跑完。

| 场景 | 旧：计数 | 新：一半 |
| --- | --- | --- |
| 1 MB/s 稳定 | 876 KB/s，p95 199 ms | 499 KB/s，p95 103 ms |
| 8 MB/s 稳定 | — | 4.0 MB/s，p95 3 ms |
| 50 MB/s 稳定 | — | 25.0 MB/s，p95 4 ms |
| 8 MB/s，指针一直在动 | 7.2 MB/s，p95 7 ms | 4.0 MB/s，p95 3 ms |
| 50 MB/s，指针一直在动 | 45.0 MB/s，p95 8 ms | 25.0 MB/s，p95 4 ms |
| 3 MB/s 每 1.7 秒减半，指针在动 | 1.74 MB/s，p95 2272 ms，最坏 3284 ms | 0.80 MB/s，p95 8 ms，最坏 10 ms |
| 50 MB/s，20 秒后永久降到 20 MB/s | 18.2 MB/s，p95 497 ms | 12.5 MB/s，p95 5 ms |
| 3.3 MB/s，接收端省电（停一下再收要多等 150 ms） | 1.67 MB/s，p95 9045 ms | 0.70 MB/s，p95 3 ms |
| 8 MB/s，接收端每次回复要 250 ms（不限速时 2.98 MB/s） | 3.03 MB/s | 1.08 MB/s |
| 按排队调速的四条（含两条减半） | 不变 | 不变 |

结论：

- 链路一变，旧做法就让实时内容排上几秒。这正是 11-12 几份现场记录里的情况。新做法在所有场景下都在 10 ms 左右，只有 1 MB/s 那条最慢的链路例外：最小的帧也要占 16 ms 链路，这条一直不切片。
- 代价是吞吐：稳定链路上大约是原来的 55%；回复很慢的接收端只剩不限速时的三分之一多一点。旧做法对这种接收端会整个放开。
- 这些代价只出现在"有键鼠或声音在走、又拿不到排队时间"的时候。电脑之间走 UDP 的正常情况是按排队调速，不受影响。

## 没测的

- 弱 Wi-Fi 实测（门禁的后一半）。
- 手机一边播放电脑的声音、一边接收大文件：最可能碰到"回复很慢"那种接收端。
- 模拟里的接收端只是几种典型行为，真实手机的存储和省电行为没有建模。
