# 2026-11-12 传文件时按键鼠包排队的时间调速

接着[用户贴的日志](2026-11-12-transfer-pacing-user-logs.md)，在小新（Windows，Core Ultra 9 185H，Wi-Fi 6E 网卡当时只连在 72 Mbps）和这台 Mac 之间复现"传文件时指针掉帧"。Mac 调试版控制小新的测试副本，同时给它发 300 MB 随机文件。指针是程序生成的，每 8 ms 一个移动。

## 先排除被控端主线程

测试副本里临时加了一个探针：另一个 isolate 每 2–3 ms 发一条带单调时钟的消息，记主 isolate 隔多久才处理到它（键鼠的 UDP 包同样要等主 isolate）。同时用 profile 版的时间线看主线程在忙什么。

| | 消息多等（p95 / p99 / 最长） |
|---|---|
| 空闲 | 0.2 / 0.2 / 1.6 ms |
| 收 300 MB（约 3 MB/s） | 0.4–3.5 / 2–6 / 5–11 ms，25 秒里一次 33 ms |

25 秒里主线程忙的时间不到 3%（画帧、处理消息）。这台机器上指针慢不在被控端主线程。传完后的半秒卡顿这次也没有复现（发的是随机文件，不是视频）。

## 卡在哪

| | 被控端指针比最快那次多等（中位 / p95 / 最长） |
|---|---|
| 不传文件 | 3–5 / 15 / 32–71 ms |
| 同时传文件 | 18–65 / 49–178 / 92–287 ms |

Mac 这边限速器的日志（每 5 秒一行）：

| 时刻 | mode | 允许 kB/s | 链路 kB/s | 发出 kB | 确认 kB |
|---|---|---|---|---|---|
| 02:52:04 | held | 2767 | 3074 | 13512 | 5406 |
| 02:52:09 | measuring | 不限 | 1946 | 18420 | 13924 |
| 02:52:14 | held | 1665 | 1849 | 0 | 7784 |
| 02:52:19 | measuring | 不限 | 1849 | 14064 | 9797 |
| 02:52:24 | measuring | 不限 | 1996 | 4144 | 9116 |
| 02:52:29 | released | 不限 | 2860 | 13155 | 12681 |

这条 Wi-Fi 实际只跑 2–3 MB/s，而且一秒一个样。限速器拿 5 分钟前量到的 3 MB/s 的九成去发，送达只有 1–2 MB/s，队列一直在长；它看到"限着发比不限时慢得多"，就切到不限速重新量，最后认定是"限着反而慢的接收端"，放开两分钟。这几段不限速的时间正是指针等 200 ms 以上的时候。

问题出在信号上：按计数调速只看两次确认之间到了多少字节，几秒才有一个数，而且分不清"链路变慢了"和"接收端慢"。

## 改法

键鼠的 UDP 通道两端本来就互发保活包。保活包在类型字节后面加上时间戳和对方时间戳的回显（旧版本只读第一个字节），两端都能算出一趟来回多久；最近 200 ms 里最短的一趟减去 30 秒里最短的一趟，就是包现在排队等了多久。传文件时让通道每 25 ms 问一次。

限速器能拿到这个数时按它调（`steered`），做法写在[UDP 通道](../internals/udp-lane.md)的"和文件传输一起"一节。要点是：平时按估出的链路能力的九成发；排队连续超过 10 ms 就下调，排得越久下调越多；排队很少时才隔一阵往上试；整个过程没有不限速的时段。

调的过程中在模拟里踩到的坑：

- 每一步都按排队减速，排队还在消化时又减，几步就减到每秒 64 KB。改成减一次之后，只要排队在缩短就不再减；排队涨到减速时的两倍以上（链路突然慢了），才马上再减。
- 慢链路上不切小片，一次发出四分之一秒的数据，自己造成排队，又被当成链路满了。按排队调速时总是切小片。
- 只看 40 ms 里有没有用满额度，慢链路上常常算出 0，就再也升不上去。改成按半秒算。
- 一直往上试（每步多 3%），排队总在目标附近，稳定链路上指针反而比原来差（p95 38–49 ms）。改成按估计的九成发，隔半秒看一次、排队不到目标一半才多试 5%；指针在动时隔 2 秒才多试 2%，和按计数时"指针在动不去探"一个道理。

## 模拟结果

`test/transfer_pacer_test.dart` 的模拟链路，指针一直在动，跑 60 秒，取后 30 秒。"多等"是某个时刻来的键鼠包要排在文件数据后面多久，取 p95。按排队调速用的是最终的参数（目标 10 ms，取 200 ms 里最短，连续两步超过才减）。模拟里排队的数是准的，没有真机上的底噪。

| 链路 | 按计数：速度 / 多等 | 按排队：速度 / 多等 |
|---|---|---|
| 稳定 3 MB/s | 2.70 MB/s / 5 ms | 2.93 MB/s / 12 ms |
| 稳定 40 MB/s | 36.0 MB/s / 8 ms | 39.3 MB/s / 15 ms |
| 3 和 2 MB/s 之间平滑起伏（周期约 3 秒） | 1.95 MB/s / 6 ms | 1.99 MB/s / 32 ms |
| 40 和 25 MB/s 之间平滑起伏 | 25.2 MB/s / 9 ms | 25.4 MB/s / 45 ms |
| 3 和 1.5 MB/s 每 1.7 秒切换 | 1.74 MB/s / 2272 ms | 1.25 MB/s / 52 ms |
| 50 和 20 MB/s 每 1.7 秒切换 | 23.7 MB/s / 3124 ms | 19.7 MB/s / 12 ms |

链路突然变慢时，按计数会排几秒的队，按排队只多等几十毫秒，代价是速度少一些。稳定和平滑变化的链路上，按排队速度不少，但多等的比按计数长：它隔一阵往上试，要排队连续超过 10 ms 才往回减，平滑变慢时会多排几十毫秒。

## 真机

同样的小新和 Mac，指针程序生成，同时传 300 MB。不限速、不动指针时这条链路跑 2.1–2.4 MB/s。被控端"多等"每 5 秒一个窗口：

| 版本 | 指针多等：中位 / p95 | 文件速度 |
|---|---|---|
| 不传文件 | 2–5 / 8–15 ms | — |
| 按计数（改之前） | 18–65 / 49–178 ms | 送达 1–2.8 MB/s |
| 按排队，目标 5 ms，取 100 ms 里最短 | 3–4 / 11–20 ms（一个窗口 37，最后一个 94） | 0.1–0.5 MB/s |
| 目标 10 ms，取 200 ms，指针在动时少试 | 4–7 / 14–26 ms | 0.7–0.9 MB/s |
| 再加"连续两步超过才减" | 5–11 / 17–26 ms（两个窗口 94–146） | 0.6–0.7 MB/s |

第一版速度掉得厉害，原因是往返时间里还有两端事件循环的等待：Mac 调试版（JIT，指针程序也跑在它的主线程上）主线程落后 15–30 ms，5 ms 的目标一直被碰到，"排队为零半秒才加速"又总被打断。开着键鼠、不传文件时量了一下读数的底噪：200 ms 里最短的一趟减去基线，中位 0.7 ms、九成在 1.8 ms 以下，但每一百个有一个超过 14 ms，最高 30 ms。于是目标放到 10 ms、看 200 ms、要连续两步超过才减速。最后两版在这条链路上的差别在波动范围之内。

这条 Wi-Fi 不传文件时指针也会偶尔多等 30–70 ms，这样的尖峰会被当成排队，所以速度只有不限速时的三分之一左右。用户那两台机器之间的链路快得多（日志里 39 MB/s），模拟里稳定的快链路速度能用到九成以上，要等用户的日志确认。

日志里 `transfer_pacing` 的 `mode` 是 `steered` 时，`queueMs` 是这 5 秒里看到的最长排队。

## 没做的

- 只共享声音时还是按计数调速：声音的 UDP 在音频 isolate 里，排队的数没有传到主 isolate。
- 对方是旧版本时没有时间戳，仍按计数调速，开头几秒仍会全速跑。
- 传完后被控端主线程卡半秒的原因还没查到。
