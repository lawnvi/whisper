# 传文件时给声音和键鼠留一成带宽

2026-11-12。接着 [11-11 的记录](2026-11-11-transfer-pacing-live.md)：那次的修复上了真机还是慢。限速在 `lib/socket/transfer_pacer.dart`（`TransferPacer`），这次整个换了做法。

## 现象和原因

用户实测：链路 50 MB/s，开着声音共享传文件只有 6–7 MB/s，开着键鼠接近 30 MB/s。Mac 向手机共享声音时发 43 MB，73 秒只走了 8 MB。

- **「声音吃紧」几乎一直成立。** 播放端在一个包到点前 35 ms 就把它交给系统，上报的「还排着多少」因此经常是 0；链路延迟到 20 ms，每次上报都是 0。限速器把它当成声音要断，每次降到六成，并把之后一分钟的上限压到这次速度的 85%。上限一次次往下压，压到写死的 12 MB/s 为止，再打六折，就是快链路上的 6–7 MB/s。
- **11-11 加的两道保险都会漏。** 「连续最多降三次」只要中间有一拍平静就清零；「不低于最近 20 秒速度的四分之一」里的「最近速度」20 秒后变成限速之后的速度。慢链路上没有那 12 MB/s 垫底，一路降到 64 kB/s。
- **开头会卡住几秒**（仿真里发现，11-11 的版本就有）。还没量到速度时，发送端等第一个确认的那一拍被当成「链路只跑得动这么多」，速率降到 64 kB/s，接着一个 512 KiB 的帧要等八秒。

用户定的方向：不是限速，是留出一点带宽，让声音和键鼠不被传文件占满。

## 现在的做法

不再读声音的状态（`AudioGroupCoordinator.audioStrained` 删了），也不再按确认来得早晚降速。只数字节：两次确认之间（隔两秒以上）对方确认了多少，就是这段时间实际送达的速度。

- 链路跑得动多少还不知道：先不限速，数两次（约五秒；还在涨就接着数，最多六次）。
- 之后限在它的九成，至少留 48 kB/s。
- 送达的不到发出的九成，或者发送端一直在等确认而送达的不到允许的九成，连续两次：链路变慢了，按送达的算。一次最多降一半。
- 隔一阵（10 秒，没变化就 30 秒、1 分钟、2 分钟）多发 5% 约三秒，全送达了就上调，马上再多发 10%、20%。连续三次都全送达，说明估得太低，放开重量一次。
- 本机事件循环落后（键鼠在等）：让到八成，连续最多三次，不低于一半。
- 限着发的速度掉到不限速时的七成以下：放开八秒核对。不限速时明显更快（1.4 倍以上），说明这台接收端不能限（见下面模拟器），放开两分钟，每次加倍，最多十分钟。
- 一帧最多等一秒；还有确认在来就不算空闲，不清状态。

没有动的：帧长（四分之一秒的量）和未确认数据的上限。

## 仿真

`test/transfer_pacer_test.dart` 里的 `_transfer`，虚拟时钟，接收端用真实的 `IncomingAckClock`。有实时流量时后半程的速度占链路的比例：

| 链路 | 速度 | 一帧最多排队 |
| --- | ---: | ---: |
| 1 MB/s | 87% | 0.16 秒 |
| 8 MB/s | 89% | 0.42 秒 |
| 50 MB/s | 89% | 0.12 秒 |
| 50 降到 20 MB/s | 20 的 90% | 约 2 秒（变慢的那一下） |
| 20 升到 50 MB/s | 50 的 90%（发现要半分钟到两分钟） | |
| 3.3 MB/s，接收端省电 | 38%（这个模型里不限速也只有四成） | |
| 8 MB/s，接收端每次确认 250 ms | 和不限速一样（被判成不能限，放开） | |
| 8 MB/s，接收端每次确认 400 ms | 不限速的四成，没有放开 | |

最后一行是没解决的：限速期间帧变小了，放开核对时每帧还是换来一次慢确认，速度回不去，于是判成「链路变慢」。

## 实测

只有模拟器。Mac 调试版发给这台 Mac 上的安卓模拟器（NAT，不限速时 3.5–5.3 MB/s，自己起伏很大，确认要晚 2–5 秒），200 MB，临时开关强制按「有实时流量」处理，同一时段和不限速交替跑：

| 做法 | 限速时 | 同时段不限速 |
| --- | ---: | ---: |
| 确认晚了就降速（11-11 的做法去掉声音信号） | 2.6 MB/s，速率卡住不动 | 5.3 |
| 只数字节，不放开 | 2.4，有时越传越慢到 0.5 | 4.2 |
| 同上，帧改成 12 ms 的量连续发 | 3.2 和 1.7，两次差一倍 | 3.5 |
| 最后的做法 | 4.1 | 3.7 |

模拟器是「每次确认都很慢」的接收端：限速以后帧和帧之间有空隙，它每收一帧就确认一次、落盘一次，收得比不限速时还慢。最后的做法在开始后约十秒把它判成不能限并放开，速度和不限速相当，但也就没有给声音和键鼠留带宽。

## 没有测的

- **真机。** 手机锁屏后 adb 离线，小新休眠，这次一台都没连上。11-11 在锁屏的小米 17 上测过「限在链路九成上下」是跑得动的（2.8–3.0 MB/s，链路 3），但那是另一套判断逻辑。
- 真的开着声音或键鼠时的听感和手感，留一成够不够。
- 两台电脑之间，Windows 和 Linux 接收端，旧版本接收端（不定时回确认）。

## 试过没有采用的

- **按声音状态分两级让路，让到链路一半为止。** 写完了，仿真也过了；用户定了「留带宽而不是限速」之后去掉。
- **用「确认晚了」找链路的上限。** 在模拟器上确认一直晚几秒，判断全错。
- **小帧连续发**，让接收端看不到空隙。发送端定时一抖就有空隙，结果不稳定；帧太多时每个空隙都换来一次确认，就是 11-11 记过的那个坑。
