# 共享声音或键鼠时传输越来越慢

> 这里的做法（确认晚了就降速、再检查有没有用）一天后被换掉了，见 [2026-11-12 的记录](2026-11-12-transfer-pacing-headroom.md)。

2026-11-11。现象：开着声音或键鼠共享时传文件，速度一路往下掉，最后只剩几 MB/s 甚至更低；关掉共享马上恢复。限速在 `lib/socket/transfer_pacer.dart`（`TransferPacer`）。

## 原因

有实时流量时，`TransferPacer` 靠三样东西判断该不该降速：声音吃紧、本机事件循环落后、对方的确认比平时来得晚。第三样有两种情况不是传输造成的，却一样会触发降速：

- **确认的时间里包含帧自己的传输时间。** 一帧是四分之一秒的数据量，最大 4 MiB。在 30 MB/s 的链路上，一个 4 MiB 的帧自己就要走 140 ms，而"平时"的基准是开头几个小帧量出来的十几毫秒。于是速度到链路的三四成就被判成排队，每秒降一次。
- **省电的接收端，收得越少回得越慢。** 锁屏的手机在流量稀的时候让 Wi-Fi 休眠，确认晚几百毫秒。降速让流量更稀，确认更晚，再降速，一直降到底。

两种情况下降速都不解决问题，原来的逻辑却会一直降下去。

## 改法

降速之后检查有没有用（`_slowingIsNoUse`）：

- 确认晚了先降一次，然后等确认反映出降速之后的情况。自己造成的排队在降速后会消退，确认会明显变快，这时只等它排空，不再多降；之后接近这个速度时慢慢涨。
- 确认还是一样晚，说明不是这次传输造成的：把这个延迟当作现在的常态（30 秒内有效），速度恢复到降速之前。
- 声音一直吃紧或本机一直落后，连续最多降三次。
- 速度不低于最近 20 秒链路实际速度的四分之一。

没有实时流量时的行为没有变。未确认数据的上限（排队时约两秒的量）也没有变，它仍然按原来的基准算。

## 实测

Mac（调试版）发给小米 17（Release 版，锁屏），2.4 GHz Wi-Fi，这条链路不限速时 2.6–3.1 MB/s。传 60 MB，强制按"有实时流量"限速，新旧交替各两次：

| --- | ---: | --- |
| 新 | 3.0 MB/s | 2.9 2.7 3.1 2.9 3.0 3.2 |
| 旧 | 0.8 MB/s（73 秒没传完） | 1.0 0.8 0.0 3.3 0.0 1.5 … 0.2 0.1 0.1 |
| 新 | 2.8 MB/s | 2.5 2.8 3.1 3.0 2.9 2.9 2.7 |
| 旧 | 0.4 MB/s（73 秒只传了 29 MB） | 0.7 1.4 1.3 0.6 … 0.1 0.1 0.1 |

## 试过没有采用的

- **有实时流量时改成小帧、每四分之一秒一批、批后等确认。** 模拟里速度和排队都好，真机上不行：接收端每回一次确认要把数据落盘一次，批越小确认越多，锁屏的手机光顾着落盘和确认，速度掉到 0.2–0.8 MB/s。低速时把帧合并、按延迟加长每批、限制每批最多翻倍，都试了，真机上仍然越传越慢。
- **只加"降速没用就撤销"，不看排队有没有消退。** 真的排队也会被撤销（降速后一秒内确认还来不及变快），模拟里排队到一两秒。

## 没有测的

- 真的开着声音或键鼠时的听感和手感。真机测试是强制按"有实时流量"限速，没有真的放声音，所以省电手机那种越稀越慢的情况比实际使用更严重。
- 两台电脑之间、接收端是 Windows 或 Linux、有线或更快的 Wi-Fi。
- 旧版本接收端（0.0.59 及之前，不会定时回确认）和文件夹传输：逻辑相同，没有单独跑。
